## Rehearsal questions

1. "You said scan reads the whole table. Is there ever a case where scan is the right choice?"
   - **Strong answer**: "For analytics or data export where you need every item. Also for small tables (< 1000 items) where the cost difference is negligible. Never for a production API hot path."

2. "Why not just use PostgreSQL with JSON columns instead of DynamoDB?"
   - **Strong answer**: "DynamoDB scales horizontally without connection pooling, sharding, or vacuum overhead. At 100K writes/second, Postgres requires significant operational investment. For < 10K writes/second with complex queries, Postgres is often the better choice."

3. "What's the hardest part of single-table design?"
   - **Strong answer**: "Designing the sort key before knowing all future access patterns. In SQL, you normalize and add indexes later. In DynamoDB, the key design is your query API — changing it requires data migration."

4. "How do you test these examples without paying for AWS?"
   - **Strong answer**: "DynamoDB Local (Docker image from AWS) emulates the full API locally. That's the next thing I'd add to this project."

5. "This is a tutorial project — how does it translate to production?"
   - **Strong answer**: "The patterns translate directly — single-table design, composite keys, conditional writes, GSIs. The difference is error handling, monitoring, and scale testing. I'd add retry logic, CloudWatch alerting, and load testing as the next maturity layer."
