# 04 — Quiz Bank

Discussion-style Q&A items powering `/learn-this-project-quiz`. Drawn from `01-knowhow-inventory.md` and `02-runbook.md`.

## How these questions are designed

1. **Questions are discussion prompts, not fill-in-the-blank.** Every prompt opens up a topic.
2. **A good answer is 3–5 sentences that names file paths AND explains the principle.** Pure recall ("the command is X") is ⚠️ partial.
3. **If a question can be answered in one sentence, it was too narrow.** Merge it into a deeper item.

### Good vs bad question shapes

- ❌ Bad: "What command installs the dependencies?" → recites `mise run inst`.
- ✅ Good: "A teammate just cloned the repo and gets `KeyError: 'AWS_PROFILE'` on their first script run — where do you point them and what's the chain of code that produced that error?" → forces them to open `.env`, `mise.toml`, and `one_03_boto_ses.py:16-21`.

- ❌ Bad: "What does `use_boto_session` do?" → one-line definition.
- ✅ Good: "Walk through why every example wraps its DynamoDB calls in `with use_boto_session(Model, bsm):`. What would happen if a learner stripped that block out?" → forces a tour of the pynamodb connection model + the `pynamodb-session-manager` rationale.

- ❌ Bad: "What is the table prefix?"
- ✅ Good: "Every script repeats `PREFIX = 'dynamodb_basic_opeartions'` at the top. Why isn't it imported from a shared constant, and what would break if a learner changed it in only one file?"

## Setup and environment

- **Q-001** [tag: runbook, difficulty: easy]
  - **Q:** A new contributor just cloned this repo and asks you what they need to type to get a working environment. Where would you point them, and what would you tell them about how the toolchain fits together?
  - **A:** Point them at `mise.toml` — it's the single source of truth for tool versions (Python 3.12, uv, claude, pandoc) and tasks. The minimum path is `mise install` (pulls all tools) → `cp .env.example .env` and set `AWS_PROFILE` → `mise run inst` (which runs `uv venv` + `uv sync --all-extras`). The reason mise sits on top of uv is that mise answers *both* "which Python?" and "what commands?" — uv only answers the dependency half. `02-runbook.md` documents this verbatim; `mise.toml` is the authority.
  - **Source:** `mise.toml`, `02-runbook.md`

- **Q-002** [tag: knowhow, difficulty: medium]
  - **Q:** A learner runs `python examples/00-minimal-poc/s01_minimal_poc.py` and gets `KeyError: 'AWS_PROFILE'`. Walk through the chain of code that produced the error, and why it doesn't fire at import time.

That code is inside the `bsm` `cached_property` (line 16), so it doesn't fire until something *reads* `one.bsm`. In `s01_minimal_poc.py`, that happens at line 55 (`bsm = one.bsm`), not at import. Fix: `cp .env.example .env`, set `AWS_PROFILE=<profile>`, rerun. The `.env` file is loaded automatically because `mise.toml:3` has `_.file = ".env"`.
  - **Source:** `dynamodb_basic_opeartions/one/one_03_boto_ses.py:14-21`, `mise.toml:1-3`

- **Q-003** [tag: runbook, difficulty: easy]
  - **Q:** What does `mise run inst` actually do, and why is it preferred over calling `uv sync` directly?
  - **A:** It's defined at `mise.toml:22-25` as `depends = ["venv-create"]` (running `uv venv --allow-existing` first) + `run = "uv sync --all-extras"`. ## Architecture and the `one` singleton

- **Q-004** [tag: knowhow, difficulty: medium]
  - **Q:** Why does the project have a separate `dynamodb_basic_opeartions/` package alongside `examples/`? Could you delete the package and inline its work into each script?
  - **A:** The package exports one thing: `from dynamodb_basic_opeartions.one.api import one`. `one.bsm` is a `BotoSesManager` cached as a `@cached_property` in `one_03_boto_ses.py:14-21` — so every example gets the same boto3 session/profile/region without re-reading credentials. You *could* inline `BotoSesManager(...)` at the top of every script, but you'd duplicate the `AWS_PROFILE` env lookup and `region_name="us-east-1"` setting in 30+ places. The package is a centralization, not a library — its job is to keep example scripts short and consistent.
  - **Source:** `dynamodb_basic_opeartions/one/one_03_boto_ses.py:14-29`, `dynamodb_basic_opeartions/one/api.py`

- **Q-005** [tag: knowhow, difficulty: medium]
  - **Q:** `OneConfigMixin` at `dynamodb_basic_opeartions/one/one_02_config.py` is empty. Why does it exist, and what would you put there?
  - **A:** It's a placeholder slot in the `class One(OneConfigMixin, OneBotoSesMixin)` composition pattern at `one_01_main.py`. Keeping the mixin in place now means future config additions are a non-breaking diff — they just go inside the existing class. A natural use would be a `DYNAMODB_ENDPOINT` override (read from env) so `OneBotoSesMixin.dynamodb_client` could be retargeted at DynamoDB Local for offline runs. The fact it's empty is intentional scaffolding, not dead code.
  - **Source:** `dynamodb_basic_opeartions/one/one_02_config.py`, `03-elevation-roadmap.md` § Developer experience

- **Q-006** [tag: knowhow, difficulty: hard]
  - **Q:** Region is hardcoded `us-east-1` at `one_03_boto_ses.py:19`. Why isn't it a config variable, and what would a senior-engineer version of that decision look like?
  - **A:** Pinning the region keeps every example reproducible — a learner can't accidentally point at `us-west-2` and wonder why their tables don't appear in the console. The cost is that anyone with credentials in only another region must edit the source. The senior-engineer move is to read `AWS_REGION` from env with `us-east-1` as default — same default behavior, override-able without source edits. This belongs in `OneConfigMixin` (currently empty), which is exactly the slot the project left open for it.
  - **Source:** `dynamodb_basic_opeartions/one/one_03_boto_ses.py:19`, `one_02_config.py`

## The `use_boto_session` idiom

- **Q-007** [tag: knowhow, difficulty: medium]
  - **Q:** Every example wraps its DynamoDB calls in `with use_boto_session(Model, bsm):`. What would happen if a learner stripped that block out, and why is this idiom necessary?
  - **A:** Without it, pynamodb falls back to its default connection — which reads credentials from the ambient environment exactly once and pins them on a module-level singleton. The script might still "work" (using the default `aws configure` profile), but it would write to whatever account boto3 happened to find, not the one bound to `one.bsm`. `use_boto_session` is the right idiom: it retargets pynamodb's connection at a specific `BotoSesManager` for the duration of the `with` block, then restores the original on exit. It comes from the external `pynamodb-session-manager` package, not pynamodb itself — common point of confusion.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py:57-62`, `pyproject.toml:21`

- **Q-008** [tag: convention, difficulty: easy]
  - **Q:** Look at any example file and you'll see `bsm = one.bsm` two lines before the `with use_boto_session(Model, bsm):` block. Why isn't `one.bsm` passed directly into the `with` statement?
  - **A:** Mostly readability — `one.bsm` is a `@cached_property`, so the second access is free, but writing out `bsm = one.bsm` once at the top signals to the reader "this is the AWS-account handle the rest of the script uses". It also makes the file self-documenting if you grep for `bsm` later. There's no functional difference; the pattern is convention, not requirement. See `s01_minimal_poc.py:55-62` for the canonical shape.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py:55-62`

## Idempotent script lifecycle

- **Q-009** [tag: knowhow, difficulty: medium]
  - **Q:** Every script begins with `if not Model.exists(): Model.create_table(wait=True)` followed by `for x in Model.scan(): x.delete()`. Walk through what each line does, and explain why the table is reused but the rows are wiped.
  - **A:** Line 1 creates the table only on the first run; subsequent runs skip it because `wait=True` would otherwise burn 5–30 seconds polling DynamoDB for the table to reach ACTIVE state. Line 2 deletes every row so a rerun starts from a clean slate. The design decision is "table reuse, row wipe": preserve the slow operation (table creation), redo the fast one (row deletion). The commented-out `# Model.delete_table()` at the end of every script is the escape hatch for when a learner *does* want to drop the table — e.g. after changing the schema. See `s01_minimal_poc.py:64-82`.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py:63-82`, `examples/README.md:26-34`

- **Q-010** [tag: mech, difficulty: medium]
  - **Q:** `scan() + delete()` for cleanup is fine on a teaching POC but would be costly at scale. Why? And what would the production-grade alternative be?
  - **A:** Every scanned item consumes 1 RCU; every delete consumes 1 WCU. A 1000-row table costs 1000 reads + 1000 writes per cleanup. The production-grade alternative is to drop and recreate the table (`Model.delete_table()` then `Model.create_table()`) — a single API call each way, no per-row cost — but you pay the 5–30s table-creation wait. For tables that need *partial* cleanup, you'd use TTL (DynamoDB's built-in expiry) instead. The POC's pattern is correct for its scale; it would be wrong as a production cleanup routine.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py:67-69`, `03-elevation-roadmap.md` § Observability

- **Q-011** [tag: knowhow, difficulty: hard]
  - **Q:** A learner adds a new attribute to the `Card` model and reruns `s01_minimal_poc.py`. The script runs fine but they don't see the new field in the AWS console. What happened?
  - **A:** DynamoDB is schemaless — adding a Python attribute to the model doesn't change the underlying table schema, because there isn't one. The new attribute will appear on rows written *after* the model change, but `Model.exists()` returns true (the table is still there) so `create_table` is skipped, and existing rows have no value for the new attribute (pynamodb treats this as `None` on read). To "reset" they uncomment `# Card.delete_table()` at the end, run once, then run again to get a fresh table. Common confusion for learners coming from relational databases.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py:63-82`, `examples/02-table-management/`

## Table prefix and cleanup

- **Q-012** [tag: convention, difficulty: medium]
  - **Q:** Every script repeats `PREFIX = "dynamodb_basic_opeartions"` at the top instead of importing it from a shared module. Why? And what breaks if a learner changes it in only one file?
  - **A:** The repetition keeps each script standalone — a learner can copy any single file out of the repo and it still runs. Centralizing the constant would couple every script to the package layout, which is exactly the friction the curriculum is trying to avoid. The cost is real: if a learner renames the prefix in `s01_minimal_poc.py` only, `cleanup_all_tables.py` won't find that table because it greps for the prefix (`examples/cleanup_all_tables.py:33`). The orphan will sit in the AWS account incurring storage. Convention beats DRY here because the audience is learners, not maintainers.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py:33`, `examples/09-pipeline-metadata-demo/models.py:18`, `examples/cleanup_all_tables.py`

- **Q-013** [tag: mech, difficulty: easy]
  - **Q:** When should a learner run `python examples/cleanup_all_tables.py`, and what does it actually do under the hood?
  - **A:** Run it at the end of any session where you don't want the curriculum's tables sitting in your account (storage is cheap but not free, and a cluttered console is annoying). Under the hood it uses raw boto3 — not pynamodb — to call `list_tables`, filter to names starting with `dynamodb_basic_opeartions`, print them for confirmation, and call `delete_table` on each. The reason it bypasses pynamodb is that it doesn't know about your Model classes; it works purely by prefix match on names.
  - **Source:** `examples/cleanup_all_tables.py`

## CRUD basics (folder 03)

- **Q-014** [tag: knowhow, difficulty: medium]
  - **Q:** A learner writes `card.save()` to "update the credit_limit" but their other fields disappear. What did they misunderstand, and what should they have done instead?
  - **A:** `save()` in pynamodb maps to DynamoDB's `PutItem`, which replaces the *entire* row identified by the hash/range key. Any field not set on the Python object becomes empty on the DynamoDB side. The right call is `card.update(actions=[Card.credit_limit.set(new_value)])` — that maps to `UpdateItem`, which is a partial update. This trap is the whole reason `examples/03-crud-basic/s01_save.py` and `s03_update.py` are separate files: the curriculum forces the learner to notice the distinction.
  - **Source:** `examples/03-crud-basic/s01_save.py`, `examples/03-crud-basic/s03_update.py`

- **Q-015** [tag: mech, difficulty: medium]
  - **Q:** Compare `Model.get(hash_key)` and `Model.query(hash_key)`. Which one returns a single item, which returns an iterator, and what error do you get when the wrong one is used?
  - **A:** `get` is a single-item lookup by full primary key — if the row doesn't exist, it raises `Model.DoesNotExist`. `query` returns an iterator over *all* items sharing that hash key (after applying any sort-key condition). Confusing them: calling `get` when there's a range key but only providing the hash key raises `TypeError: get() missing 1 required positional argument: 'range_key'`; calling `query` when you wanted a single item silently iterates and you get the first item with `next(...)`. Examples `03/s02_get.py` and `05/s01_query_basic.py` show the right shapes.
  - **Source:** `examples/03-crud-basic/s02_get.py`, `examples/05-query-and-scan/s01_query_basic.py`

- **Q-016** [tag: knowhow, difficulty: medium]
  - **Q:** Why does `s05_refresh.py` exist? When would you reach for `instance.refresh()` over just calling `Model.get(...)` again?
  - **A:** `refresh()` re-reads the row from DynamoDB and mutates the same Python object in place; `get()` returns a brand-new instance. The difference matters when other code holds a reference to the original object — e.g., in a long-running optimistic-lock retry loop where you've passed the `card` instance into helper functions. `refresh()` keeps those references valid; `get()` would leave them holding the stale version. See `examples/03-crud-basic/s05_refresh.py` for the simple shape and `06/s03_optimistic_lock.py:57-93` for where this matters.
  - **Source:** `examples/03-crud-basic/s05_refresh.py`, `examples/06-condition-expression/s03_optimistic_lock.py`

## Batch and unprocessed items (folder 04)

- **Q-017** [tag: knowhow, difficulty: medium]
  - **Q:** The `with Model.batch_write() as batch:` block in `s01_batch_write.py` looks like a transaction but isn't. What's actually happening on `__exit__`, and how is this different from `TransactWrite`?
  - **A:** On `__exit__`, pynamodb flushes the queued writes in chunks of 25 (DynamoDB's batch limit). Each chunk is a single API call but every item is processed independently — there's no atomicity, no conditions, and partial success is normal. `TransactWrite` is the opposite: up to 100 items, all-or-nothing, supports per-item conditions, 2× the cost. The rule: `batch_write` for bulk inserts where partial success is fine; `TransactWrite` when you need ACID. Folder 07 walks the latter explicitly.
  - **Source:** `examples/04-batch-operations/s01_batch_write.py`, `examples/07-transactions/s01_transact_write.py`

- **Q-018** [tag: knowhow, difficulty: hard]
  - **Q:** Walk through `s03_batch_with_unprocessed.py`. What is "UnprocessedItems", why does it happen, and what's the retry pattern?
  - **A:** DynamoDB enforces per-partition write throughput. When a batch hits a hot partition or capacity wall, the server returns 200 OK with a partial success — the items it couldn't process are listed under `UnprocessedItems` in the response. **It is not an error.** The retry pattern is: read `UnprocessedItems`, sleep with exponential backoff, resubmit just those items, repeat until empty. Learners who don't handle this silently drop rows on every batch run. The curriculum makes this a dedicated script because it's the single most-likely production bug from folder 04.
  - **Source:** `examples/04-batch-operations/s03_batch_with_unprocessed.py`

## Query vs scan (folder 05)

- **Q-019** [tag: knowhow, difficulty: medium]
  - **Q:** A teammate proposes "let's just use scan everywhere — it's simpler". How do you push back, using a specific example from the repo?
  - **A:** Scan reads every row in the table and bills you for it; query reads only rows under one partition key. `examples/05-query-and-scan/s04_scan_and_filter.py` and `s01_query_basic.py` make this concrete: a query for `Card.holder_name == "Alice"` is 1 RCU when there's one Alice; a scan with the same filter is N RCUs where N is the row count, *regardless of whether the filter matches*. The filter is applied *after* the bill. On a 100K-row table, that's a 100,000× cost difference. Scan exists for one-off admin tasks; routine reads must be queries.
  - **Source:** `examples/05-query-and-scan/s01_query_basic.py`, `examples/05-query-and-scan/s04_scan_and_filter.py`

- **Q-020** [tag: mech, difficulty: medium]
  - **Q:** `s02_query_sort_and_limit.py` uses `scan_index_forward=False` to get the latest items first. What's the underlying storage detail that makes this so cheap, and would `Model.scan(...)[::-1]` be equivalent?
  - **A:** DynamoDB stores items within a partition sorted by the range key — `scan_index_forward=False` just reads the partition's B-tree in reverse, so getting the latest N rows is as cheap as getting the earliest N rows. `Model.scan()` reads the *whole table* and then you'd reverse the in-memory list, which is O(table size) reads + O(N) memory. `scan_index_forward=False` + `limit=N` is the right idiom for "give me the most recent N events for X".
  - **Source:** `examples/05-query-and-scan/s02_query_sort_and_limit.py`

- **Q-021** [tag: knowhow, difficulty: hard]
  - **Q:** `s03_query_pagination.py` walks pagination explicitly. But `Model.scan()` also paginates — the iterator does it under the hood. Why is the explicit version worth a dedicated script?
  - **A:** Because the implicit pagination hides what's really happening. The iterator can do unbounded round-trips to DynamoDB and you'd never see the boundary — that's how a "this scan worked fine locally" becomes a "we burned through the day's RCU budget" incident. The explicit `last_evaluated_key` loop in `s03_query_pagination.py` forces the learner to see one round-trip per page, count them, and decide where to stop. It's a "show the seams" beat.
  - **Source:** `examples/05-query-and-scan/s03_query_pagination.py`

## Conditions and optimistic locking (folder 06)

- **Q-022** [tag: knowhow, difficulty: medium]
  - **Q:** `s01_save_if_not_exists.py` uses `save(condition=Model.hash_key.does_not_exist())`. Why is this the only way to "insert but not overwrite", and what would the wrong-way attempt look like?
  - **A:** DynamoDB's `PutItem` is unconditional by default — there is no separate "insert" verb. The wrong-way attempt is to `Model.get(...)` first to check existence, then `save()` if absent: this has a TOCTOU race where two callers can both see "absent" and both write, with the second silently overwriting the first. The `condition=...` form pushes the check to the server inside the same atomic write — the server rejects the put if the key exists, raising `PutError`. This is the only correct pattern.
  - **Source:** `examples/06-condition-expression/s01_save_if_not_exists.py`

- **Q-023** [tag: knowhow, difficulty: hard]
  - **Q:** Walk through `s03_optimistic_lock.py`. Why is the version counter incremented manually here when pynamodb has a `VersionAttribute` class that does it automatically?
  - **A:** Deliberate teaching choice. The script implements the read-version → attempt-update-with-condition → catch-`UpdateError` → reload-and-retry loop *by hand* so the learner sees what `VersionAttribute` is doing under the hood. In a real codebase you'd swap to `VersionAttribute` for the automatic version and the auto-condition; that's a one-line change once you understand the mechanism. The script is at `examples/06-condition-expression/s03_optimistic_lock.py:57-93`. This is the same pedagogical move as folder 11's three M:N approaches: show the explicit mechanism first, library convenience second.
  - **Source:** `examples/06-condition-expression/s03_optimistic_lock.py`

- **Q-024** [tag: knowhow, difficulty: medium]
  - **Q:** Conditions can apply to both `save()` (PutItem) and `update()` (UpdateItem). Where would you use each, with a concrete example from the curriculum?
  - **A:** `save(condition=...)` is for "insert OR replace, but only if the precondition holds" — `s01_save_if_not_exists.py` uses `condition=Card.card_id.does_not_exist()` to make `save()` strictly an insert. `update(condition=...)` is for "modify one or more fields, but only if the precondition holds" — `s02_update_with_condition.py` uses something like `update(actions=[Card.credit_limit.set(20000)], condition=Card.credit_limit == old_value)` to refuse the update if another writer changed `credit_limit` since you read it. The split mirrors the underlying DynamoDB API: PutItem vs UpdateItem each take their own ConditionExpression.
  - **Source:** `examples/06-condition-expression/s01_save_if_not_exists.py`, `examples/06-condition-expression/s02_update_with_condition.py`

## Transactions (folder 07)

- **Q-025** [tag: knowhow, difficulty: hard]
  - **Q:** Walk through `s02_transact_with_condition.py` — the money-transfer pattern. Which operations are inside the transaction, what condition fails the whole thing, and what's the cost in WCUs?
  - **A:** The transfer is two updates inside `TransactWrite`: debit the source account (with `condition=Account.balance >= amount`) and credit the destination account (unconditional). If the debit condition fails — source has less than `amount` — DynamoDB aborts the whole transaction; neither account changes. The cost is 2× a normal write per item, so a 2-item transfer is 4 WCUs, not 2. That's the price of ACID across rows. If the same logic were done as two non-transactional `update()`s, a crash between them would leave money missing.
  - **Source:** `examples/07-transactions/s02_transact_with_condition.py`

- **Q-026** [tag: mech, difficulty: medium]
  - **Q:** `TransactWrite` needs an explicit `Connection` object instantiated up front. Why isn't this a method on `Model` like `save()` is?
  - **A:** Because a single transaction can span multiple Models and multiple tables — there's no single Model class that "owns" the call. The `Connection(region=...)` object is the API surface for table-agnostic operations. In `examples/07-transactions/s01_transact_write.py` you'll see `conn = Connection(region=bsm.aws_region)` then `with TransactWrite(connection=conn) as tx: tx.save(item_a); tx.save(item_b)`. This shape catches first-time learners — they expect `Model.transact_write(...)` and the API isn't there.
  - **Source:** `examples/07-transactions/s01_transact_write.py`, `examples/11-single-table-many-to-many/s01_adjacency_list.py:34-35,86-88`

- **Q-027** [tag: knowhow, difficulty: hard]
  - **Q:** When would you reach for `TransactGet` (`s03_transact_get.py`) over just reading the items individually with `get()`?
  - **A:** `TransactGet` gives you a *consistent snapshot* across multiple items — DynamoDB guarantees the reads reflect the same point in time even though they hit multiple rows (and possibly multiple tables). Sequential `get()` calls don't: another writer could change row B between your read of A and your read of B, and you'd see an inconsistent pair. The cost is, again, 2× normal RCUs. Use it when "consistent view across N rows" is a correctness requirement — e.g., checking source + destination account balances together before deciding whether a transfer is safe.
  - **Source:** `examples/07-transactions/s03_transact_get.py`

## Secondary indexes (folder 08)

- **Q-028** [tag: knowhow, difficulty: medium]
  - **Q:** `s01_gsi_basic.py` declares a GSI as a subclass of `GlobalSecondaryIndex` on the Model. Walk through how that maps to DynamoDB at table-creation time and at query time.
  - **A:** At `create_table()`, pynamodb reads the GSI subclass's `Meta.index_name` and the `hash_key=True` / `range_key=True` flags on its attributes, builds a `GlobalSecondaryIndexes` block in the CreateTable request, and DynamoDB provisions an asynchronously-maintained index. At query time, `Model.<gsi_attr>.query(key)` routes the request to that index — the GSI has its own primary key space and is queried independently of the main table. Writes to the main table propagate to the GSI asynchronously, which is why GSI reads are always eventually consistent.
  - **Source:** `examples/08-gsi-and-lsi/s01_gsi_basic.py`, `examples/09-pipeline-metadata-demo/models.py:21-35`

- **Q-029** [tag: knowhow, difficulty: hard]
  - **Q:** `s02_gsi_projections.py` shows `AllProjection` vs `KeysOnlyProjection`. Walk through what each one stores and the tradeoff a designer is making.
  - **A:** `AllProjection` copies every attribute of the main-table row into the GSI — queries get the full item without a second round-trip but the GSI is roughly the same size as the main table (double storage cost). `KeysOnlyProjection` stores only the GSI's keys plus the main table's keys — minimal storage, but a query that needs attributes has to do a fetch on the main table after the GSI lookup (2 round-trips). Real-world rule of thumb: `AllProjection` if the GSI is rarely queried or the rows are tiny; `KeysOnlyProjection` if storage matters and you can tolerate the second fetch. There's also `IncludeProjection` (project some attributes) as a middle ground.
  - **Source:** `examples/08-gsi-and-lsi/s02_gsi_projections.py`

- **Q-030** [tag: knowhow, difficulty: hard]
  - **Q:** `s03_lsi_basic.py` shows an LSI. Compare it to a GSI on the same dimensions — when is LSI the right pick, and what's its hard constraint?
  - **A:** LSI shares the main table's hash key but adds an alternate sort key; GSI has both its own hash and sort key. The unique LSI features are (a) strong-consistent reads (GSI can't offer this) and (b) inclusion in the main table's RCU/WCU budget (no separate provisioning). The hard constraint is the **10 GB-per-hash-key limit**: once any one partition exceeds 10 GB total (main + all LSIs), writes to that partition fail. LSIs also must be declared at table-creation time and cannot be added or removed later; GSIs can be added/removed live. Use LSI when you need strong-consistent reads on an alternate sort and your per-partition data is bounded.
  - **Source:** `examples/08-gsi-and-lsi/s03_lsi_basic.py`

- **Q-031** [tag: knowhow, difficulty: hard]
  - **Q:** `s04_gsi_vs_scan.py` does a head-to-head cost comparison. What's the principle the script is teaching, and what numbers would convince a teammate "GSI not scan"?
  - **A:** The principle is that adding a GSI is almost always cheaper than scanning the main table — even after factoring in extra write cost (every main-table write also writes the GSI). The script measures `ConsumedCapacity` on both paths so the learner sees the gap as a real number, not an abstraction. Convincing numbers usually look like: GSI query = 1–3 RCUs regardless of table size; scan + filter = `table_size_kb / 4` RCUs (the filter is applied *after* the bill). On a 1 MB table the gap is ~80×; on a 1 GB table it's 80,000×.
  - **Source:** `examples/08-gsi-and-lsi/s04_gsi_vs_scan.py`

## Single-table design (folders 09–11)

- **Q-032** [tag: knowhow, difficulty: medium]
  - **Q:** The `09-pipeline-metadata-demo/` is the first multi-script folder with a shared `models.py`. What's the pedagogical reason for this break in convention, and what new pattern is the learner being introduced to?
  - **A:** Up through folder 08, each script defines its Model inline so the script is self-contained. Folder 09 introduces the real-world pattern: **the Model lives in a shared module, and operational scripts import from it**. `s01_setup.py`, `s02_seed_data.py`, `s03_queries.py`, and `s04_compare_capacity.py` all import `PipelineRun` from `examples/09-pipeline-metadata-demo/models.py`. The lesson is "this is how production code is organized" — the inline-model convention is a teaching simplification, not a recommendation.
  - **Source:** `examples/09-pipeline-metadata-demo/models.py`, `examples/09-pipeline-metadata-demo/s01_setup.py`

- **Q-033** [tag: knowhow, difficulty: hard]
  - **Q:** Why does `PipelineRun` in folder 09 have a `StatusIndex` GSI keyed on `(run_status, start_ts)` instead of just adding a filter to the main-table query?
  - **A:** The main table's primary key is `(pipeline_name, run_id)` — queries must start with `pipeline_name`. Asking "all FAILED runs across all pipelines" can't be a main-table query; the only main-table alternative is `scan` + filter on `run_status`, which is expensive (O(table size)). The `StatusIndex` GSI keyed on `(run_status, start_ts)` answers the question with a single `query("FAILED")` and gives time-ordered results for free because `start_ts` is the GSI's range key. That's the canonical reason to add a GSI: an access pattern your primary key can't serve.
  - **Source:** `examples/09-pipeline-metadata-demo/models.py:21-35`

- **Q-034** [tag: knowhow, difficulty: hard]
  - **Q:** The `Entity` model in `10-single-table-one-to-many/models.py` has seven entity-specific fields all marked `null=True`. Walk through why this is the price of single-table design and what alternative shapes a learner might consider before accepting it.
  - **A:** Single-table design stores multiple entity types (CUSTOMER / CARD / TRANSACTION) in one table; rows of different types have different fields, so almost every attribute is nullable from the table's perspective. The `Entity` class therefore has a union of all three entity types' fields. Alternatives: (a) one Model class per entity type with the same `Meta.table_name` — cleaner Python, but pynamodb has rough edges for this pattern; (b) three separate tables — cleaner schema, but loses the "one query returns customer + all their cards + all their transactions" benefit that's the whole point of single-table. Accepting the wide nullable model is the standard tradeoff.
  - **Source:** `examples/10-single-table-one-to-many/models.py:21-43`

- **Q-035** [tag: knowhow, difficulty: hard]
  - **Q:** In `10-single-table-one-to-many`, the SK for a transaction row is `f"TX#{card_id}#{ts.isoformat()}"`. Walk through *why* this composite shape lets a single range query answer "all transactions on card CD001 between T1 and T2".
  - **A:** Items in a DynamoDB partition are sorted by SK. With this format, all transaction rows for a customer sort first by card_id, then by timestamp within that card. So `query(PK="CUSTOMER#C001", SK between "TX#CD001#T1" and "TX#CD001#T2")` matches exactly the transactions on `CD001` in that time window — the `TX#CD001#` prefix nails the card, the timestamp range narrows the window. No GSI required, single round-trip. Move the components around (`f"TX#{ts}#{card_id}"`) and the query becomes impossible because the time bounds wouldn't be a contiguous SK range. The order of fields in the composite SK *is* the access pattern.
  - **Source:** `examples/10-single-table-one-to-many/s01_setup_and_seed.py:20-21`, `examples/10-single-table-one-to-many/s03_query_card_transactions_by_date.py`

- **Q-036** [tag: knowhow, difficulty: hard]
  - **Q:** Folder 11 demonstrates three M:N approaches for Customer ↔ Merchant. Walk through the tradeoff matrix: write cost, read cost, consistency.
  - **A:** Adjacency list (`s01`): 2 writes per edge (atomic via `TransactWrite`), 1 main-table query in either direction, strong consistency both ways. GSI inversion (`s02`): 1 write per edge, 1 main-table query forward (strong) + 1 GSI query reverse (eventual). Composite GSI (`s03`): 1 write per edge with extra `gsi_pk`/`gsi_sk` fields, GSI queries everywhere (all eventual), but the same GSI serves multiple relationship types so it's cheaper at scale. Pick by primary axis: strict consistency → adjacency list; write cost matters and reverse-direction can be slightly stale → GSI inversion; many relationship types → composite GSI.
  - **Source:** `examples/11-single-table-many-to-many/s01_adjacency_list.py`, `s02_gsi_inversion.py`, `s03_composite_gsi.py`

- **Q-037** [tag: knowhow, difficulty: hard]
  - **Q:** In `s01_adjacency_list.py`, edges are written via `TransactWrite` instead of `batch_write`. What goes wrong if you swap in `batch_write`?
  - **A:** `batch_write` does not provide atomicity: the forward edge (`CUSTOMER#C001 → MERCHANT#M001`) and the backward edge (`MERCHANT#M001 → CUSTOMER#C001`) are separate items, and the API may succeed on one and fail on the other. You'd end up with a half-edge — the graph is inconsistent and "merchants for C001" disagrees with "customers for M001". `TransactWrite` is the only DynamoDB primitive that makes "both rows or neither row" a server-side guarantee. The cost is 2× per item but correctness wins for the relationship graph.
  - **Source:** `examples/11-single-table-many-to-many/s01_adjacency_list.py:67-74`

- **Q-038** [tag: knowhow, difficulty: hard]
  - **Q:** In `s02_gsi_inversion.py`, the `InversionIndex` swaps the main table's PK and SK. Walk through how that lets one row serve a bidirectional relationship at half the write cost.
  - **A:** One row is written: `(pk="CUSTOMER#C001", sk="MERCHANT#M001")`. The `InversionIndex` GSI is defined with `hash_key = sk` and `range_key = pk`, so DynamoDB indexes that same row a second time as `(MERCHANT#M001, CUSTOMER#C001)`. Forward query — "merchants for C001" — hits the main table, strong consistency. Reverse query — "customers for M001" — hits the GSI, eventual consistency. Same row, two access patterns, one write. The price is the eventual-consistency tail on reverse queries, which is usually milliseconds.
  - **Source:** `examples/11-single-table-many-to-many/s02_gsi_inversion.py:47-54`

- **Q-039** [tag: knowhow, difficulty: hard]
  - **Q:** The three folder-11 scripts each use a different table name (`_st_mtm_adjacency`, `_st_mtm_gsi_inversion`, `_st_mtm_composite_gsi`). Why? And what would break if they shared one table?
  - **A:** Each script demonstrates a *different schema* for the same problem — different keys, different (or absent) GSIs. They can't share a table because they disagree about what the primary key means. Splitting them lets the learner run all three demos back-to-back and compare; cleanup catches all three because they share the project prefix. If they shared a table, the second script's `create_table` would silently fail (table exists with a different schema) or the rows from one approach would pollute the other's queries.
  - **Source:** `examples/11-single-table-many-to-many/s01_adjacency_list.py:46`, `s02_gsi_inversion.py`, `s03_composite_gsi.py`

## Cross-cutting and project-level

- **Q-040** [tag: convention, difficulty: medium]
  - **Q:** None of the example scripts have an `if __name__ == "__main__":` guard. Walk through why this is a deliberate choice and what it costs.
  - **A:** Top-level procedural code is the simplest possible shape — a learner reads top-to-bottom with no indirection. The cost: you can't `import` an example into a test without triggering side-effects, you can't dispatch to one of several behaviors per script, and tooling like `pytest --collect-only` will run the example. For a teaching POC the readability win is bigger than the testability loss. `cleanup_all_tables.py:29` is the lone exception because it has an interactive `input("delete? y/N")` and would be dangerous to fire on import. See `03-elevation-roadmap.md` § Code organization for the senior-engineer next step.
  - **Source:** `examples/00-minimal-poc/s01_minimal_poc.py`, `examples/cleanup_all_tables.py:29`

- **Q-041** [tag: knowhow, difficulty: medium]
  - **Q:** Why does the project run on **real AWS DynamoDB** instead of DynamoDB Local? What would the senior-engineer upgrade look like?
  - **A:** Real DynamoDB matches every API quirk a learner will hit in production — GSI eventual consistency, partition throttling, real error responses. DynamoDB Local approximates these and silently differs on some. The cost is that a learner without an AWS account can't run the curriculum. The senior-engineer upgrade is an env-var toggle (`USE_DYNAMODB_LOCAL=1`) wired through the currently-empty `OneConfigMixin` so learners can choose. See `03-elevation-roadmap.md` § Developer experience.
  - **Source:** `dynamodb_basic_opeartions/one/one_03_boto_ses.py`, `03-elevation-roadmap.md` § Developer experience

- **Q-042** [tag: deps, difficulty: medium]
  - **Q:** Look at `pyproject.toml:16-21`. Why is `boto3-stubs[dynamodb]` pinned alongside `boto3`, and what would happen if they drift?
  - **A:** `boto3-stubs` is type-stub-only — it adds nothing at runtime, just powers editor autocomplete and mypy hints for `boto3.client('dynamodb')` calls. Pinning them together means autocomplete matches the real API. If they drift (e.g., a learner upgrades `boto3` manually), the IDE may suggest methods that don't exist yet (or omit ones that do), but runtime is unaffected. It's a developer-experience pin, not a correctness pin.
  - **Source:** `pyproject.toml:16-21`

- **Q-043** [tag: runbook, difficulty: medium]
  - **Q:** `mise run test` and `mise run cov` are both defined in `mise.toml` but both fail. Why? And what's missing to make them work?
  - **A:** Both tasks invoke `.venv/bin/pytest tests`, but there is no `tests/` directory in the repo — `pytest` exits with "file or directory not found". The `pytest`/`pytest-cov` packages are installed (via the `test` extra in `pyproject.toml:43-45`), so the harness is ready; only the tests are missing. Adding tests is the highest-leverage upgrade in `03-elevation-roadmap.md`.
  - **Source:** `mise.toml:38-46`, `pyproject.toml:43-45`, `03-elevation-roadmap.md` § Test depth

- **Q-044** [tag: knowhow, difficulty: hard]
  - **Q:** Curriculum-level: the project intentionally goes from "one model per script" (folders 00–08) to "shared `models.py`" (folder 09) to "single-table multi-entity model" (folders 10–11). What's the learning arc, and what would you tell a learner who tried to skip folder 09?
  - **A:** The arc is one-table-per-entity → one-table-per-domain (shared model module) → one-table-many-entities (single-table design). Each step adds a layer of co-location: more entities, fewer tables, more access patterns from one query. Folder 09 is the bridge — it's the simplest *real* model module (one entity, one GSI) and teaches the "models live in their own file" pattern without the complexity of multi-entity discrimination. A learner who jumps from folder 08 to folder 10 will land cold on three new patterns at once (shared module + multi-entity model + composite SK). The recommendation in `examples/README.md:62-69` makes this explicit.
  - **Source:** `examples/README.md:62-69`, `examples/09-pipeline-metadata-demo/`, `examples/10-single-table-one-to-many/`

- **Q-045** [tag: knowhow, difficulty: medium]
  - **Q:** The project name `dynamodb_basic_opeartions` contains a typo — `opeartions` instead of `operations`. Why hasn't it been fixed, and what would break if you fixed it now?
