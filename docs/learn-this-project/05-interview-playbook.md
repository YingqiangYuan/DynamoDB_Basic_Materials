# 05 — Interview Playbook

Production-grade interviewer questions that probe reasoning and tradeoffs. Powers `/learn-this-project-interview`. Drawn from `01-knowhow-inventory.md` + `03-elevation-roadmap.md`.

**Skill-side rule:** Never read model answers verbatim to the candidate. They are the interviewer's grading reference. Surface specific *gaps* only at the debrief.

## Opening — the 90-second pitch (model script)

> I built a progressive DynamoDB curriculum — 12 numbered folders walking from a five-step "create table → save → get" skeleton up through single-table design (1:N hierarchies, three flavors of M:N). The substance is in `examples/`; the `dynamodb_basic_opeartions` package is a thin wrapper that exposes one `BotoSesManager` singleton so every script gets the same AWS session.
>
> The choices I treated as load-bearing: pynamodb as the ORM (over raw boto3) because the DynamoDB-JSON marshalling layer is its own learning curve; PAY_PER_REQUEST billing everywhere so the curriculum doesn't have a "provisioned capacity" topic; idempotent script lifecycle (`create-if-missing` + `scan-then-delete`) so a learner can re-run any script safely.
>
> The climax is folders 09–11. Folder 09 is the first multi-script module, folder 10 walks 1:N single-table design, and folder 11 shows three working M:N approaches with their tradeoffs — adjacency list, GSI inversion, composite GSI. That's where the "DynamoDB is access-pattern-first, not schema-first" mindset clicks.
>
> What's missing: a real test suite (`tests/` doesn't exist; `mise run test` is broken), CI (no `.github/workflows/`), and a DynamoDB Local toggle for offline runs. Those are my next three priorities.

The skill should listen and note: did the candidate name folders 09–11 as the climax? Did they mention the gaps unprompted? Did they justify pynamodb over boto3?

## Round 1 — What you have

### Q1.1 — Walk me through what happens when I run `python examples/00-minimal-poc/s01_minimal_poc.py` for the first time

- **Model answer:** Imports trigger no side-effects. Line 55 reads `bsm = one.bsm`, which lazily constructs a `BotoSesManager` from `AWS_PROFILE` (from `.env`) — first AWS touchpoint. `with use_boto_session(Card, bsm):` retargets pynamodb's connection. `Card.exists()` returns False, so `Card.create_table(wait=True)` runs — that's the 5–30s wait while DynamoDB transitions the table to ACTIVE. Scan-then-delete is a no-op on empty. `Card(...).save()` is a PutItem. `Card.get("CD001")` is a single-key read. Print. Done.
- **Follow-ups:** "Why does the create_table wait take 5–30s but the second run takes ~2s?" "What's different about the import chain if AWS_PROFILE isn't set?"
- **Weak answer signature:** Reciting the script line-by-line without naming pynamodb's lazy connection model or the `cached_property` on `bsm`.

### Q1.2 — Walk me through the `dynamodb_basic_opeartions/one/` package. Why does it exist as a separate package and not just inline in `examples/`?

- **Model answer:** It exposes one thing: `one.bsm`, a cached `BotoSesManager` bound to `AWS_PROFILE` and `us-east-1`. Every example imports `from dynamodb_basic_opeartions.one.api import one` and uses `one.bsm`. Centralizing the construction means example scripts stay short — one import line, no credential plumbing. The `cached_property` decorator on `bsm` means it's built once per Python process and reused. It's not a reusable library, it's a centralization to keep the substance (`examples/`) lean.
- **Follow-ups:** "Why is region hardcoded? Where would you make it configurable?" "What's `OneConfigMixin` for if it's empty?"
- **Weak answer signature:** Calling it "a wrapper" without explaining what the `cached_property` actually buys, or treating it as a library.

### Q1.3 — Explain the role of `use_boto_session` and why every script uses it

- **Model answer:** pynamodb defaults to a module-level connection that picks up credentials from the ambient environment exactly once. `use_boto_session(Model, bsm)` is from the external `pynamodb-session-manager` package — it temporarily replaces pynamodb's connection with one bound to a specific `BotoSesManager` for the duration of the `with` block. On exit, the original is restored. This makes the project's "centralized AWS session" idea actually work — without it, pynamodb might pick up *different* credentials than `one.bsm`. Common confusion: it looks like a pynamodb feature but isn't.
- **Follow-ups:** "What happens if a script doesn't use the `with` block?" "Can you run two `with use_boto_session` blocks bound to different accounts in the same process?"
- **Weak answer signature:** Describing it as "a context manager" without naming the connection-routing mechanism or the source package.

### Q1.4 — Walk me through the idempotent script lifecycle and why it's shaped that way

- **Model answer:** Every script does `if not Model.exists(): create_table(wait=True)` then `for x in Model.scan(): x.delete()`. The asymmetric design — *table* reused, *rows* wiped — is because `create_table(wait=True)` blocks 5–30s while DynamoDB activates the table, and that's not worth paying on every rerun. Row deletion is fast (single API call per row). The commented-out `# Model.delete_table()` at the bottom is the escape hatch when a learner does want to start from a blank schema. The pattern shows up in every script verbatim because the substance of each lesson belongs after the lifecycle prologue.
- **Follow-ups:** "What does `scan + delete` cost on a 100K-row table?" "What if I add a new attribute to the model — will I see it in the table?"
- **Weak answer signature:** Reciting the code without articulating why it's asymmetric (table preserved, rows wiped).

### Q1.5 — Walk me through the single-table design in folder 10. What's the access pattern, what does the SK encode, and why?

- **Model answer:** One table holds CUSTOMER, CARD, TRANSACTION rows. PK is `CUSTOMER#<id>` so all of a customer's data sits in one partition. SK is one of `PROFILE`, `CARD#<card_id>`, or `TX#<card_id>#<iso_timestamp>` — the composite SK encodes the card_id first, timestamp second, so "all transactions on card CD001 between T1 and T2" is a single range query (`SK between TX#CD001#T1 and TX#CD001#T2`). The order of components in the SK *is* the access pattern. If you swapped to `TX#<ts>#<card_id>`, the same query would be impossible because the time bounds wouldn't be contiguous. That's the whole single-table design lesson: design the keys around the queries, not around the entities.
- **Follow-ups:** "What's the price of single-table? Show me in the model definition." "How would you handle the access pattern 'all transactions over $1000 last week, any customer'?"
- **Weak answer signature:** Naming the entities without explaining the composite-SK ordering as a *design choice* tied to a specific access pattern.

## Round 2 — What you'd elevate

### Q2.1 — What's the biggest gap in this project?

- **Model answer:** No test suite. `mise run test` and `mise run cov` both reference a `tests/` directory that doesn't exist; they'll fail immediately. `pytest` and `pytest-cov` are installed via the `test` extra, so the harness is ready — only the tests are missing. The senior-engineer fix is a `conftest.py` that starts DynamoDB Local in Docker and exposes it via a fixture, then one test file per example folder. That unlocks CI (which doesn't exist either — no `.github/workflows/`) and dependency-drift detection. Everything else compounds once tests exist.
- **Follow-ups:** "Why not just run the examples against real AWS in CI?" "What's the gotcha with `moto` for testing DynamoDB?"
- **Weak answer signature:** "I'd add tests" without articulating the infrastructure (DynamoDB Local fixture, pytest scopes, the broken `mise.toml` task as evidence).

### Q2.2 — Walk me through how you'd add DynamoDB Local support without breaking the existing examples

- **Model answer:** Add `DYNAMODB_ENDPOINT` to `OneConfigMixin` (currently empty at `dynamodb_basic_opeartions/one/one_02_config.py`). When set, override `dynamodb_client` to point at it (boto3's `endpoint_url` kwarg). For pynamodb-specific routing, set `Meta.host` on the Model — pynamodb-session-manager already handles the routing, so we just need to thread the endpoint into the boto3 session. A `scripts/dev-up.sh` brings up `amazon/dynamodb-local:latest` and exports the var. Backward-compatible — unset means real AWS, same as today. The empty `OneConfigMixin` is the right place because the project already left that slot for exactly this kind of config.
- **Follow-ups:** "What behavior of real DynamoDB does Local *not* simulate well?" "How does this interact with the `use_boto_session` flow?"
- **Weak answer signature:** Proposing the change without naming `OneConfigMixin` as the existing slot for it.

### Q2.3 — How would you make the single-table keys in folders 10–11 type-safe?

- **Model answer:** Today the keys are hand-rolled strings: `f"CUSTOMER#{customer_id}"`, `tx_sk(card_id, ts) = f"TX#{card_id}#{ts.isoformat()}"`. The senior-engineer move is one `@dataclass` per entity with `to_pk()` / `to_sk()` methods plus a `parse(pk, sk)` for reads. Now key construction is centralized, typo-resistant, testable. The current cost: a separator typo in one script silently breaks queries in another — there's no compiler to catch it. The upgrade is small (~50 lines) and would pay for itself the first time someone forgets the `#`.
- **Follow-ups:** "Why not use a library like `dynamodb-toolbox` (JS)?" "What's the test you'd write to verify the key DSL?"
- **Weak answer signature:** "Add type hints" without proposing the dataclass + parse() shape.

## Round 3 — Alternatives considered

### Q3.1 — Why pynamodb over boto3?

- **Model answer:** The lesson surface is data modeling and access patterns, not DynamoDB-JSON marshalling. boto3's low-level `client('dynamodb').put_item(...)` requires you to wrap every value in `{'S': 'string'}` / `{'N': '42'}` envelopes — that layer is its own learning curve and would drown the actual lesson. pynamodb handles the marshalling, lets you define `class Card(Model)` with native attributes, and exposes `query` / `scan` / `update` as methods on the class. The tradeoff is one more dependency and slightly less control. For a teaching POC, pynamodb wins. For a production service where you need raw control, boto3 might be the right answer.
- **Follow-ups:** "Where does pynamodb's abstraction leak? Show me a case in the curriculum." "Why not the boto3 *Resource* layer (`boto3.resource('dynamodb')`)?"
- **Weak answer signature:** Answering "it's higher-level" without naming the DynamoDB-JSON marshalling problem.

### Q3.2 — Why PAY_PER_REQUEST billing everywhere?

- **Model answer:** Two reasons. First, the curriculum's tables are mostly empty or small — PAY_PER_REQUEST removes the "did I provision enough capacity?" topic from the lessons, which would be a tangent. Second, learners shouldn't have to think about throttling on idle tables. The price: at sustained ~>20% utilization, provisioned would be cheaper. For a teaching POC, this is the wrong axis to optimize. For production, the right answer is to look at access patterns first and pick.
- **Follow-ups:** "Where would you teach the provisioned mode if you added it back?" "What's the cost gap on a 100 req/sec sustained workload?"
- **Weak answer signature:** Defending PAY_PER_REQUEST as universally better; not acknowledging the utilization breakpoint.

### Q3.3 — Why `boto-session-manager` instead of vanilla `boto3.Session`?

- **Model answer:** `BotoSesManager` adds three things on top of `boto3.Session`: profile-name + region wired in one place, cached lazy clients (`bsm.dynamodb_client` is built once and reused), and a uniform shape across our sibling repos. The third is the real reason — every project in the same author's ecosystem uses `one.bsm`, so muscle memory transfers. Vanilla `boto3.Session` works fine; bsm is a small ergonomics win that compounds across many projects. Not a hard requirement.
- **Follow-ups:** "If I wanted to assume an IAM role for the curriculum, how would that change?" "What's the failure mode if bsm and boto3 versions drift?"
- **Weak answer signature:** Treating bsm as load-bearing; not acknowledging that vanilla `boto3.Session` would work.

### Q3.4 — Folder 11 shows three M:N approaches. Walk me through when you'd pick each in production

- **Model answer:** Adjacency list (two rows + `TransactWrite`) when strict consistency in both directions matters more than write cost — e.g., authorization checks, financial relationships. GSI inversion (one row + inverted GSI) when write cost matters and the reverse direction can tolerate ms-level staleness — e.g., user-follower relationships in social. Composite GSI (dedicated `gsi_pk`/`gsi_sk`) when one table holds many relationship types and a single GSI can serve all of them — denormalized graphs, recommendation models. The rule: pick by the primary axis you're optimizing (consistency / write cost / GSI count) and accept the others.
- **Follow-ups:** "When does adjacency list break down at scale?" "If you have to add a fourth relationship type later, which approach handles it best?"
- **Weak answer signature:** Defaulting to one approach as "the best"; not articulating the axis-trade.

## Round 4 — Problems hit

### Q4.1 — A teammate adds a new attribute to the `Card` model and reruns `s01_minimal_poc.py`. The script runs fine but they don't see the new field in existing rows in the AWS console. What happened?

- **Model answer:** DynamoDB is schemaless — adding a Python attribute doesn't change the underlying table because there is no schema to change. `Card.exists()` returns True, so `create_table` is skipped, and existing rows just don't carry the new attribute (pynamodb reads `None`). New writes get it; old rows never will. To fully reset, uncomment `# Card.delete_table()` and run twice. Classic confusion for learners coming from Postgres.
- **Follow-ups:** "How would you backfill the new attribute on the existing rows?" "What if the new attribute were `hash_key=True`? Same fix?"
- **Weak answer signature:** Blaming pynamodb without explaining DynamoDB's schemalessness.

### Q4.2 — A batch_write seems to "succeed" but ~10% of items are silently missing. Walk me through the cause and the fix.

- **Model answer:** DynamoDB returns 200 OK on `BatchWriteItem` even when it couldn't process some items — they come back in the response's `UnprocessedItems` field. **Not an error**, it's a partial-success contract. The caller must read `UnprocessedItems`, sleep with backoff, resubmit, and loop until empty. `s03_batch_with_unprocessed.py` exists specifically to teach this. Most beginners only check the exception path and assume "no exception = all written" — silent data loss.
- **Follow-ups:** "What triggers UnprocessedItems? Capacity? Hot partition? Both?" "Would `TransactWrite` solve this?"
- **Weak answer signature:** Suggesting retry on exception only; missing the partial-success-on-200 contract.

### Q4.3 — A learner's optimistic-lock retry loop never terminates under contention. What's likely wrong and how do you debug?

- **Model answer:** Likely: they're catching the wrong exception and re-reading from a stale Model instance instead of a fresh one. The shape in `s03_optimistic_lock.py:57-93` is: catch `UpdateError` (the conditional check failure), call `instance.refresh()` (re-fetches the row with current version), increment locally, retry. The two common bugs: (a) catching `Exception` broadly and ignoring genuine errors, (b) re-fetching with `Model.get(...)` into a *new* instance and forgetting to swap references, so the next attempt uses the old version again. Add a `max_attempts` ceiling and log the version delta each retry to make the cycle visible.
- **Follow-ups:** "What's the failure mode if two writers hit the same row exactly simultaneously, every retry?" "When would you switch from optimistic to pessimistic locking?"
- **Weak answer signature:** "Add a sleep" without naming `refresh()` and the UpdateError catch.

## Round 5 — Production pushbacks

### Q5.1 — Suppose traffic on the pipeline_runs table 100x'd overnight. What breaks first?

- **Model answer:** Read traffic — the `StatusIndex` GSI is the cheaper read path and would absorb most of it, but GSI writes propagate from the main table asynchronously. At 100x, the propagation lag grows and "all FAILED runs" queries return stale results for longer. Second risk: `s04_compare_capacity.py`'s scan calls become catastrophically expensive — scans were already the wrong tool, now they're a self-DOS. Third: `create_table(wait=True)` calls in init scripts queue if multiple processes start cold simultaneously. Mitigations: switch to provisioned with auto-scaling for predictable cost, drop the scan demos from prod, accept higher GSI lag or move to strong-consistent main-table queries.
- **Follow-ups:** "Would you change the partition key design?" "What's the right metric to alert on?"
- **Weak answer signature:** Naming "add cache" without identifying GSI propagation lag or scan cost.

### Q5.2 — A P0 fires: customer C001's transactions are returning duplicates. Walk me through your debugging steps.

- **Model answer:** Hypothesis: a stale GSI is returning duplicates that no longer exist in the main table. Step 1: query the main table directly (`Entity.query("CUSTOMER#C001", Entity.sk.startswith("TX#"))`) and compare counts — main table is ground truth. Step 2: if main matches expected and the duplicates only appear in a GSI-backed view, it's GSI propagation lag or a stuck index — file with AWS, fall back to main-table queries until resolved. Step 3: if main table has duplicates too, check the writer — likely a missing condition on `save()` letting the same TX be written twice. Look at the composite SK; the `ts.isoformat()` component is the unique anchor. Step 4: postmortem — add `condition=Entity.sk.does_not_exist()` to the writer.
- **Follow-ups:** "What if the duplicates have different timestamps but the same logical event?" "How would you write a dashboard query to detect this?"
- **Weak answer signature:** Jumping to "add a UNIQUE constraint" (DynamoDB doesn't have those across rows) or "use TransactWrite" without identifying main-vs-GSI as ground truth.

### Q5.3 — A dependency vanishes from PyPI: `pynamodb-session-manager` is yanked. What's your immediate response and your long-term fix?

- **Model answer:** Immediate: pin the last known-good version in `pyproject.toml` (`pynamodb-session-manager>=0.1.2,<1.0.0` already does this) and use `uv.lock` to reproduce. Mirror the package source somewhere if needed. Long-term: `use_boto_session` is ~50 lines of code — it's worth inlining into the project as a vendor copy with attribution, or replacing with a thin custom wrapper that does the same connection swap. The dependency is small enough that owning the code is reasonable insurance. Document the inlining clearly so future readers know it came from upstream.
- **Follow-ups:** "How does this change your CI design?" "Would you vendor `boto-session-manager` too? Why or why not?"
- **Weak answer signature:** "Find a replacement" without acknowledging the option to vendor or the existing pin/lock protection.
