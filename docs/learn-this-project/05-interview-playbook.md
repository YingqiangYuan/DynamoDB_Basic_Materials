# 05 — Interview Playbook

## Opening — the 90-second pitch

> "I built a progressive tutorial project for Amazon DynamoDB using pynamodb, a Python ORM. It starts from a minimal model definition and walks through 12 example folders covering CRUD, batching, query/scan, conditional writes, ACID transactions, secondary indexes, and single-table design — all in a fin-tech credit-card domain. Each example is independently runnable against a real AWS account. The capstone demonstrates single-table design for 1:N and M:N relationships, which is the mental model shift from SQL normalization to access-pattern-first design. I also built a shared credential management layer using pynamodb-session-manager for multi-account support."

## Round 1 — What you have (mechanism understanding)

### Q1.1: Walk me through what happens when you run one of the example scripts end-to-end.

**Model answer:** The script imports `one.bsm` (a BotoSesManager singleton configured from `AWS_PROFILE` in `.env`, targeting `us-east-1`). It defines a pynamodb Model class with attributes and a `Meta` inner class specifying the table name (prefixed with `dynamodb_basic_opeartions_`). The Model is wrapped in `with use_boto_session(Model, bsm):`, which swaps pynamodb's underlying DynamoDB connection to use the configured credentials. Inside the context, the script creates the table if needed, wipes existing rows for idempotency, seeds fresh data, then demonstrates the specific operation (e.g., query, scan, transaction). Results are printed to stdout.

**Follow-ups:** "Where does the credential swap actually happen under the hood?" / "What if you forgot the `use_boto_session` wrapper?"

**Weak answer:** Describes running `python script.py` without explaining the credential/session mechanism or idempotency pattern.

### Q1.2: Explain the architecture of the `dynamodb_basic_opeartions.one` package.

**Model answer:** It's a singleton pattern using mixin composition. `One` inherits from `OneConfigMixin` (placeholder config) and `OneBotoSesMixin` (provides `bsm`, `boto_ses`, `dynamodb_client` as cached properties). The singleton `one = One()` is exported from `one/api.py`. Every example imports it via `from dynamodb_basic_opeartions.one.api import one`. Changing AWS credentials means editing one file (`one_03_boto_ses.py`), and all 40+ example scripts automatically follow.

**Follow-ups:** "Why cached properties instead of regular attributes?" / "What's the failure mode if the AWS profile doesn't exist?"

**Weak answer:** Describes the import but can't explain the mixin pattern or the centralization benefit.

### Q1.3: How does the single-table design in folder 10 work? Walk me through the key schema.

**Model answer:** One table stores Customers, Cards, and Transactions. PK is always `CUSTOMER#<id>`. SK differentiates entity types: `PROFILE` for the customer, `CARD#<card_id>` for cards, `TX#<card_id>#<timestamp>` for transactions. This co-location means a single `query(pk='CUSTOMER#C001')` returns the customer profile and all their cards and transactions. Range conditions on SK (e.g., `begins_with(SK, 'CARD#')`) let you query just one entity type within a partition. The timestamp in the transaction SK enables date-range queries without a separate index.

**Follow-ups:** "What happens if a customer has a million transactions?" / "How would you add a 'most recent 10 transactions' query?"

**Weak answer:** Can describe the PK but struggles to explain the SK design or the access patterns it enables.

### Q1.4: How do DynamoDB transactions work in this project? Give me the money-transfer example.

**Model answer:** Folder 07 demonstrates TransactWrite with a money-transfer pattern: debit Account A and credit Account B atomically. The transaction bundles both UpdateItem operations — if either fails (e.g., insufficient balance checked via condition expression), neither is applied. pynamodb wraps this in `TransactWrite(connection=conn)` with `conn.add(update_action)` for each item. Transactions cost 2x normal capacity because DynamoDB uses a two-phase commit across partitions.

**Follow-ups:** "What's the maximum number of items in a transaction?" / "When should you NOT use transactions?"

**Weak answer:** Knows transactions exist but can't articulate the atomicity guarantee or the cost tradeoff.

### Q1.5: Explain the difference between `query` and `scan` and how folder 05 demonstrates the cost difference.

**Model answer:** `query` uses the partition key to go directly to the right partition — cost is proportional to the result set. `scan` reads every item in the table, applying filters server-side — cost is proportional to the table size regardless of how many items match. Folder 05 demonstrates this progressively: `s01` does a basic query, `s04` shows scan with filters and notes that consumed capacity doesn't decrease even though fewer items are returned. Folder 09's `s04_compare_capacity.py` makes the cost argument concrete by printing RCU consumption for both approaches.

**Follow-ups:** "When is scan acceptable?" / "How does pagination interact with query cost?"

**Weak answer:** Knows query is "better" but can't explain why in capacity-unit terms.

## Round 2 — What you'd elevate (3–6 more months)

### Q2.1: If you had 3 more months on this project, what's the #1 thing you'd add and why?

**Model answer:** Local DynamoDB testing. Right now, every run hits a real AWS account, which means you need credentials, pay for capacity, and can't run in CI. With DynamoDB Local in Docker, all examples could run offline, CI could validate them on every push, and new users wouldn't need an AWS account to get started. The implementation is straightforward — pynamodb's `Meta.host` attribute supports endpoint override.

**Follow-ups:** "What about Moto instead of DynamoDB Local?" / "What DynamoDB features does DynamoDB Local not simulate?"

**Weak answer:** Picks something cosmetic (better README, more comments) or can't articulate the ROI of their choice.

### Q2.2: The project has no CI/CD. How would you design a CI pipeline for a project where every test requires a DynamoDB backend?

**Model answer:** GitHub Actions with a Docker service running `amazon/dynamodb-local:latest`. The workflow installs deps with `mise run inst`, starts DynamoDB Local on port 8000, sets an environment variable (e.g., `DYNAMODB_ENDPOINT=http://localhost:8000`) that the `one` singleton reads, then runs each example script as a test. Separately, `mise run cov` runs unit tests with coverage reported to Codecov. The key insight is separating integration tests (examples against DynamoDB Local) from unit tests (package code).

**Follow-ups:** "How do you handle table creation latency in CI?" / "What if DynamoDB Local and real DynamoDB behave differently?"

**Weak answer:** Proposes mocking DynamoDB away entirely or doesn't address the endpoint-switching mechanism.

### Q2.3: What advanced DynamoDB patterns are missing from this project that a production system would need?

**Model answer:** TTL for automatic item expiration (e.g., transactions older than 90 days), DynamoDB Streams for event-driven processing (e.g., fraud detection on new transactions), write sharding for hot partitions, and DAX for read-heavy caching. The project intentionally focuses on data modeling over operational patterns — extending it to cover TTL and Streams would round out the learning path.

**Follow-ups:** "How does TTL work at the storage level?" / "What's the tradeoff of Streams vs polling?"

## Round 3 — Alternatives considered

### Q3.1: Why pynamodb instead of raw boto3 for these examples?

**Model answer:** pynamodb provides a declarative Model/Attribute layer that maps naturally to DynamoDB's schema. For a teaching project, this is critical — learners think in terms of "Customer has a name and email" (pynamodb) rather than `{'S': 'John'}` (boto3). The tradeoff: pynamodb abstracts some DynamoDB details (like consumed capacity tracking), which is why folder 09 drops to boto3 for the capacity comparison. If this were a production system, the choice depends on whether the team values ORM ergonomics over raw API control.

**Follow-ups:** "When would you prefer raw boto3?" / "What about dynamodb-toolbox or electrodb in other languages?"

**Weak answer:** "pynamodb is simpler" without articulating what's gained and lost.

### Q3.2: Why single-table design instead of one table per entity?

**Model answer:** DynamoDB charges per request and doesn't support JOINs. If Customer, Card, and Transaction are in separate tables, loading a customer's dashboard requires 3 separate queries. Single-table design puts them in one table with composite keys, so one `query(pk='CUSTOMER#C001')` returns everything. The tradeoff: the table is harder to understand visually, entity-specific operations require careful SK design, and adding a new entity type means extending the key schema. Multi-table is easier to reason about but costs more at scale.

**Follow-ups:** "When does single-table design NOT make sense?" / "How do you handle schema evolution in a single table?"

**Weak answer:** "It's the DynamoDB best practice" without explaining the access-pattern reasoning.

### Q3.3: The project uses `use_boto_session` for credential management. Why not just set `AWS_DEFAULT_PROFILE` globally?

**Model answer:** `use_boto_session` allows credential switching within a single script — you could query one account, then switch to another without restarting Python. A global env var is one-shot. For this project, the distinction is academic (all examples use one account), but the pattern teaches multi-account awareness, which is essential for AxiomCard's production setup where data lives across accounts.

**Follow-ups:** "Show me where in the code this context manager would matter for multi-account" / "What happens if you nest two `use_boto_session` calls?"

### Q3.4: Why did you organize as 12 separate folders instead of one big script or a notebook?

**Model answer:** Each folder isolates one concept, making it safe to modify without breaking others. A learner can jump to folder 06 (conditions) without reading folders 00–05. Notebooks would add richer output but are harder to run headless, harder to diff in git, and less transferable to production code. The tradeoff: 12 folders means more boilerplate (each script imports `one`, wraps in `use_boto_session`), but that repetition is actually a feature — it reinforces the pattern.

**Follow-ups:** "Would you organize differently for a team onboarding tool vs a self-study tool?"

## Round 4 — Problems hit

### Q4.1: A user reports that their example script hangs for 30 seconds before any output appears. What's happening?

**Model answer:** Most likely `create_table(wait=True)` — DynamoDB table creation takes 5–30 seconds. Check if the table already exists (it should if they've run the script before). If it's a first run, this is expected. If the table exists and it still hangs, check network connectivity to `us-east-1` or whether the DynamoDB endpoint is reachable.

**Follow-ups:** "How would you make the scripts detect this and give feedback to the user?" / "What's the difference between `wait=True` and polling?"

### Q4.2: You're running batch_write with 1000 items and some writes are silently lost. How do you debug this?

**Model answer:** Check `UnprocessedItems`. pynamodb's `batch_write` context manager handles chunking (25 per request) but if DynamoDB throttles, items land in the unprocessed response. Folder 04's `s03_batch_with_unprocessed.py` demonstrates this. In production, you'd implement retry with exponential backoff for unprocessed items. To debug: enable `return_consumed_capacity='TOTAL'`, check for `ProvisionedThroughputExceededException` in CloudWatch, and verify the table's capacity settings.

**Follow-ups:** "Is batch_write atomic?" / "What's the difference between throttling and an item-level error?"

### Q4.3: Two scripts are running concurrently against the same table and you're seeing inconsistent data. What's going on?

**Model answer:** DynamoDB is eventually consistent by default. If one script writes and another reads immediately, the read may return stale data. For the examples, this is compounded by the idempotency pattern — both scripts wipe all rows at startup, so they're stomping on each other. Fix: don't run scripts concurrently against the same table. For production, use strongly consistent reads (`consistent_read=True`) or conditional writes with version attributes.

## Round 5 — Production pushbacks

### Q5.1: Your DynamoDB table handles 100 writes/second now. What happens at 100,000 writes/second?

**Model answer:** If using on-demand billing, DynamoDB auto-scales but has an initial burst limit and a gradual ramp-up period — sudden spikes (0 → 100K WPS) can throttle for minutes until capacity adapts. If provisioned, you'll exceed your WCU limit immediately. Beyond scaling mode: check for hot partitions — if one PK receives disproportionate writes, that partition throttles even if total capacity is sufficient. Fix: write sharding (random PK suffix) to spread load. Also consider whether all 100K writes are necessary — can some be batched or deduped upstream?

**Follow-ups:** "How does on-demand billing handle a cold table that suddenly gets 100K WPS?" / "What's the per-partition limit?"

### Q5.2: A P0 fires: your DynamoDB table is returning stale data to customers. Walk me through your incident response.

**Model answer:** First, identify whether reads are eventually consistent or strongly consistent. If eventually consistent, switch critical reads to `consistent_read=True` — this costs 2x RCU but guarantees freshness. If already strongly consistent, check for GSI queries (always eventually consistent) being used where they shouldn't be. Check CloudWatch for throttling (throttled reads return empty, which looks like missing data). If the issue is GSI lag, consider switching the read path to the base table for critical queries and using the GSI only for analytics.

**Follow-ups:** "How would you set up monitoring to catch this before customers notice?" / "What's the SLA for GSI replication lag?"

### Q5.3: Your DynamoDB table has 500 million items and a new business requirement needs a query pattern that doesn't match any existing key or index. What do you do?

**Model answer:** Options in priority order: (1) Add a GSI that matches the new query pattern — can be added to an existing table without downtime. (2) If the query pattern requires a different partition key AND sort key than any existing GSI, and you're at the 20-GSI limit, consider whether an existing GSI can be repurposed with a composite key. (3) If the pattern is fundamentally incompatible with DynamoDB's key-value model (e.g., full-text search, complex aggregations), consider adding ElasticSearch/OpenSearch via DynamoDB Streams for that specific query. (4) Evaluate whether this is a sign that the table's access patterns have outgrown the original design.

**Follow-ups:** "How long does a GSI backfill take on 500M items?" / "What happens to write throughput during GSI backfill?"
