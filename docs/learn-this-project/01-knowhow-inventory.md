# 01 — Knowhow Inventory

The complete inventory of every meaningful component in `dynamodb_basic_opeartions` and **the WHY behind each one**. This is the spine of the `/learn-this-project-absorb` skill.

## Project at a glance

`dynamodb_basic_opeartions` is a progressive, hands-on POC for **Amazon DynamoDB via [pynamodb](https://pynamodb.readthedocs.io/)**. The curriculum lives entirely in `examples/`: twelve numbered folders (`00-minimal-poc` through `11-single-table-many-to-many`) that walk a learner from a five-step "create table → save → get" skeleton up through single-table-design patterns (1:N hierarchy, three flavors of M:N). Every script runs against real AWS DynamoDB in `us-east-1`, routes through a shared `boto-session-manager` singleton (`one.bsm`), and is idempotent so the learner can re-run any file safely. The whole project is built around the AxiomCard fin-tech credit-card domain so the examples form one coherent narrative (Customer → Card → Transaction → Merchant).

The deliberate name typo — `opeartions` instead of `operations` — is preserved as the project's actual name. Every file path, table name, and import uses it; treat it as canonical.

## Architecture overview

```
.
├── pyproject.toml        ← package metadata + locked deps (pynamodb, boto3, bsm)
├── mise.toml             ← single source of truth for tasks and tool versions
├── .env.example          ← AWS_PROFILE=...  (only env var the project needs)
├── dynamodb_basic_opeartions/   ← thin runtime: the `one` singleton + BotoSesManager
│   └── one/
│       ├── one_01_main.py        ← class One(OneConfigMixin, OneBotoSesMixin)
│       ├── one_02_config.py      ← (config slot, currently empty)
│       ├── one_03_boto_ses.py    ← cached_property bsm / boto_ses / dynamodb_client
│       └── api.py                ← from ...one_01_main import one
└── examples/             ← the entire curriculum lives here
    ├── README.md         ← table-of-contents + conventions every folder follows
    ├── cleanup_all_tables.py
    └── 00 .. 11/         ← 12 progressive lesson folders, each self-contained
```

The package is **not a reusable library**. Its only job is to expose `one.bsm` so every example script gets the same `BotoSesManager`-bound DynamoDB session without re-reading `AWS_PROFILE` and re-creating boto3 clients. The substance is in `examples/`.

## Component inventory

### dynamodb_basic_opeartions/one/ (the runtime)

- **Name:** `dynamodb_basic_opeartions.one.api.one`
  - **What:** A module-level singleton instance of `One`, the project's central access object for AWS.
  - **Why:** Every example script needs the same `BotoSesManager` (profile + region + cached clients). Centralizing the construction lets the examples stay short — one import line gets you `one.bsm` and your `use_boto_session(...)` block.
  - **Key files:** `dynamodb_basic_opeartions/one/api.py`, `one_01_main.py`.
  - **Depends on:** `boto3`, `boto-session-manager`, environment variable `AWS_PROFILE`.
  - **Gotchas:** Reading `os.environ["AWS_PROFILE"]` happens **lazily** inside `bsm`'s `cached_property` (`one_03_boto_ses.py:16`). The error only fires the first time something touches `one.bsm`, not at import time. If `.env` is missing, you get a `KeyError` deep in a script. Fix: copy `.env.example` to `.env` and edit before running anything.

- **Name:** `OneBotoSesMixin` (`dynamodb_basic_opeartions/one/one_03_boto_ses.py:14`)
  - **What:** Three `cached_property` accessors — `bsm`, `boto_ses`, `dynamodb_client`.
  - **Why:** `cached_property` means the `BotoSesManager` (and downstream `boto3.Session`) is built exactly once per process and reused. Avoids reading credentials on every call and keeps the global `one` cheap to import.
  - **Depends on:** `boto_session_manager.BotoSesManager`.
  - **Gotchas:** Region is **hardcoded** to `us-east-1` at `one_03_boto_ses.py:19`. If a learner wants another region, they edit that file directly — there is no env var override. WHY (best guess; verify with project owner): a teaching project doesn't justify the extra config surface; pinning the region keeps every example reproducible without surprise routing.

- **Name:** `OneConfigMixin` (`dynamodb_basic_opeartions/one/one_02_config.py`)
  - **What:** Configuration slot, currently empty.
  - **Why:** Placeholder for future config (e.g., `dynamodb_endpoint`, table prefix override). Keeping the mixin shape now means the eventual addition is a non-breaking diff. WHY (best guess; verify with project owner): the project was scaffolded with the standard `One()`-composition pattern from sibling repos; this one happens not to need config yet.

### examples/ shared conventions

- **Name:** Table-name prefix `dynamodb_basic_opeartions`
  - **What:** Every example sets `Meta.table_name = f"{PREFIX}_<suffix>"`, where `PREFIX = "dynamodb_basic_opeartions"` is repeated at the top of each script.
  - **Why:** A single prefix lets `cleanup_all_tables.py` find every table this project created in your AWS account with one regex match. It also prevents collision with other projects in the same account.
  - **Key files:** `examples/00-minimal-poc/s01_minimal_poc.py:33`, `examples/09-pipeline-metadata-demo/models.py:18`, every other example.
  - **Gotchas:** The prefix is repeated by hand in each file rather than imported from a shared constant. If a learner renames it in one file, they must rename it everywhere — or `cleanup_all_tables.py` will miss the orphan.

- **Name:** `use_boto_session(Model, bsm)` block
  - **What:** A context manager from `pynamodb_session_manager` that, inside the `with` block, routes every DynamoDB call made through `Model` through the boto3 session bound to `bsm`. On exit, the original connection settings are restored.
  - **Why:** pynamodb's default behavior is to read AWS credentials from the ambient environment exactly once and hold them on a module-level connection. `use_boto_session` is the right idiom for "I have a specific `BotoSesManager` and I want this code path to use it instead". It also makes multi-account work possible in a single process.
  - **Key files:** Every example script. Idiomatic anchor: `examples/00-minimal-poc/s01_minimal_poc.py:62`.
  - **Gotchas:** It's NOT a built-in pynamodb feature. Newcomers may assume it is. It comes from the external `pynamodb-session-manager` package (pinned in `pyproject.toml`). If a learner tries to skip the `with` block, the examples may silently fall back to the default credential chain and write to the wrong AWS account.

- **Name:** Idempotent "create-if-missing + scan-then-delete" lifecycle
  - **What:** Every script starts with `if not Model.exists(): Model.create_table(wait=True)` then `for x in Model.scan(): x.delete()` before doing anything else.
  - **Why:** Lets a learner re-run a single script many times without `create_table` taking 5–30 seconds every time and without stale rows from a prior run polluting the demo. The table is left in place across reruns; only the rows are wiped.
  - **Key files:** `examples/00-minimal-poc/s01_minimal_poc.py:64-69`, every other example.
  - **Gotchas:** `scan() + delete()` is fine on a teaching POC but is O(N) reads + O(N) writes, billed per item. A learner running examples thousands of times can rack up dollars. Also: if the table schema changes (e.g., a new attribute is added), the script doesn't recreate — it reuses the old table. Drop and rerun is `# Model.delete_table()` (commented out at the end of every file).

### examples/ folder-by-folder

- **Name:** `examples/README.md`
  - **What:** Index of all 12 folders + the four "conventions every folder follows" + suggested learning order.
  - **Why:** The on-ramp doc. It exists so a learner who clones the repo can read one file and know where to start, in what order, and what to expect. The folder list is also the single source of truth for which folders are independent (00–08) vs sequential (09–11).
  - **Read-vs-run:** This one is **READ**; you do not execute it.

- **Name:** `00-minimal-poc/s01_minimal_poc.py`
  - **What:** ~80-line "golden reference" that does the full pynamodb lifecycle in one script: define `Card` model → create table → wipe → save → get → print.
  - **Why:** A single canvas the learner can return to when they're trying to remember "the shape" of a pynamodb script. Every later script is a variation on this one.
  - **Gotchas:** Run it FIRST. If this script can't reach AWS, none of the others will either — fixing this script is the fastest way to verify the environment.

- **Name:** `01-attributes/` (3 scripts)
  - **What:** `s01_basic_types.py` (Unicode/Number/Boolean/UTCDateTime), `s02_collection_types.py` (UnicodeSetAttribute, ListAttribute), `s03_json_attribute.py` (nested dict storage).
  - **Why:** Map Python types to DynamoDB types. The lesson is *what's available* and the special-case modifiers (`null=True`, `default=...`).
  - **Gotchas:** `UnicodeSetAttribute` is an unordered set, not a list — order is NOT preserved, and DynamoDB rejects empty sets entirely. `JSONAttribute` serializes to a String type, which is opaque to DynamoDB indexing; you can't query inside it.

- **Name:** `02-table-management/` (3 scripts)
  - **What:** `s01_create_and_delete.py`, `s02_describe_table.py`, `s03_billing_modes.py` (`PAY_PER_REQUEST` vs `PROVISIONED`).
  - **Why:** Table lifecycle and capacity choice. The single biggest teaching beat: PAY_PER_REQUEST removes a class of "did I provision enough?" worries at the price of higher per-request cost above ~20% utilization. The POC defaults to PAY_PER_REQUEST everywhere.
  - **Gotchas:** `create_table(wait=True)` blocks the script until the table is ACTIVE — that's the 5–30s wait the idempotent pattern is built to avoid.

- **Name:** `03-crud-basic/` (5 scripts)
  - **What:** `s01_save.py` (PutItem semantics — full replace, not partial update), `s02_get.py` (hash + optional range), `s03_update.py` (UpdateItem actions), `s04_delete.py`, `s05_refresh.py` (re-fetch into the same Python object).
  - **Why:** Establishes the four CRUD verbs **and the trap**: `save()` is PutItem and replaces the entire row; if you want to change one field, you use `update(actions=[...])`. Beginners frequently call `save()` to "update" and silently destroy other fields.
  - **Gotchas:** `save()` overwrites by default. To make it conditional ("only insert if not exists") you must add `condition=Model.hash_key.does_not_exist()` — that's the bridge from 03 to 06.

- **Name:** `04-batch-operations/` (3 scripts)
  - **What:** `s01_batch_write.py` (up to 25 items/request), `s02_batch_get.py`, `s03_batch_with_unprocessed.py` (retry loop for the items DynamoDB refused).
  - **Why:** The shape of `with Model.batch_write() as batch:` is non-obvious — it's a session that flushes on `__exit__`. And **UnprocessedItems is not an error**: DynamoDB will partially complete a batch and hand you back the leftovers, expecting you to retry. Learners who don't know this will silently drop rows.
  - **Gotchas:** Batch ops are NOT transactional — no atomicity, no conditions, no rollback. Use `TransactWrite` (folder 07) when you need all-or-nothing.

- **Name:** `05-query-and-scan/` (4 scripts)
  - **What:** `s01_query_basic.py`, `s02_query_sort_and_limit.py` (`scan_index_forward=False`), `s03_query_pagination.py` (`last_evaluated_key` loop), `s04_scan_and_filter.py`.
  - **Why:** The single most important read-side distinction in DynamoDB: **query** uses the key, scan reads everything. Folder 05 walks the cost gap and shows when scan is the wrong tool. Pagination is a separate beat because the result iterator hides it by default.
  - **Gotchas:** `Model.scan()` returns an iterator that auto-paginates client-side. That's convenient but masks how many round-trips you actually made. On a large table this can produce surprise bills.

- **Name:** `06-condition-expression/` (3 scripts)
  - **What:** `s01_save_if_not_exists.py`, `s02_update_with_condition.py`, `s03_optimistic_lock.py`.
  - **Why:** Where DynamoDB's correctness guarantees live. `condition=...` is the *only* way to express "do this only if X is still true" at the data layer. Folder 06 walks the three canonical uses: insert-only-if-absent, conditional-update, and a hand-rolled optimistic-lock version counter.
  - **Gotchas:** When a condition fails, pynamodb raises a `PutError`/`UpdateError` (or `ItemDoesNotExist`-derived) — catching the right exception type matters. The optimistic-lock script (`s03`) shows the read-then-write loop with retry, but in a real system you'd put a `VersionAttribute` on the model to automate it. The script does it by hand deliberately so the learner sees the mechanism.

- **Name:** `07-transactions/` (3 scripts)
  - **What:** `s01_transact_write.py`, `s02_transact_with_condition.py` (money-transfer pattern), `s03_transact_get.py`.
  - **Why:** ACID across multiple items in one call. `TransactWrite(connection=conn)` is the lever — every item gets its own condition, and if any fail, none commit. The money-transfer script is the moment the learner understands why this exists.
  - **Gotchas:** `TransactWrite` needs an explicit `pynamodb.connection.Connection(region=...)` object. It is NOT a method on a Model. The first learner attempt usually trips on this. Also: transactions are 2× the cost of equivalent non-transactional writes — folder 11's adjacency-list example uses them anyway because correctness wins, but folder 11's GSI-inversion example explicitly trades them away for 1× cost + eventual consistency.

- **Name:** `08-gsi-and-lsi/` (4 scripts)
  - **What:** `s01_gsi_basic.py`, `s02_gsi_projections.py` (`AllProjection` vs `KeysOnlyProjection`), `s03_lsi_basic.py`, `s04_gsi_vs_scan.py` (cost comparison).
  - **Why:** Secondary indexes are the single biggest mechanism for cheaply unlocking new access patterns. Folder 08 walks the spectrum: GSI (own keys, separate throughput, eventual consistency, anywhere on the table), LSI (shared hash key, strong consistency, 10 GB cap per partition), projection choices (which attributes get copied into the index).
  - **Gotchas:** GSI reads are **eventually consistent**. Period. There is no strong-consistent GSI read. Beginners assume otherwise and ship bugs. LSIs allow strong reads but the size cap is real — once any one partition hits 10 GB, writes to that partition fail.

### examples/ — the climax (single-table design)

- **Name:** `09-pipeline-metadata-demo/` (composite demo)
  - **What:** A shared `models.py` defining `PipelineRun` with a `StatusIndex` GSI, plus four scripts: `s01_setup.py` (idempotent table creation), `s02_seed_data.py`, `s03_queries.py` (main-table and GSI access patterns), `s04_compare_capacity.py` (`ConsumedCapacity` for query vs scan).
  - **Why:** The first script in the curriculum that splits **one model definition across multiple scripts**. The lesson is "in real code, your model module is shared and the scripts call into it". It's also the first time the learner sees a GSI used to answer a query the primary key can't ("all runs in status FAILED").
  - **Key files:** `examples/09-pipeline-metadata-demo/models.py:21-35` (StatusIndex), `models.py:37-62` (PipelineRun).
  - **Gotchas:** `s01_setup.py` does **not** run `s02_seed_data.py` for you — the scripts must be run in order. If a learner runs `s03_queries.py` against an empty table, they get nothing back and assume the GSI is broken.

- **Name:** `10-single-table-one-to-many/` (1:N hierarchy)
  - **What:** A single `Entity` model that holds three entity types (CUSTOMER, CARD, TRANSACTION) in one table. PK is `CUSTOMER#<id>`, SK is one of `PROFILE`, `CARD#<card_id>`, or `TX#<card_id>#<iso_timestamp>`. Three scripts: `s01_setup_and_seed.py`, `s02_query_patterns.py`, `s03_query_card_transactions_by_date.py` (range query on the composite SK).
  - **Why:** The single most important DynamoDB pattern: **co-locate the entities you'll query together under the same PK so one query returns everything**. The composite SK (`TX#<card_id>#<ts>`) is the trick that makes "all transactions on card CD001 between T1 and T2" a single range query.
  - **Key files:** `examples/10-single-table-one-to-many/models.py:21-43`, `s01_setup_and_seed.py:20-21` (tx_sk format).
  - **Gotchas:** The `Entity` model has ~7 entity-specific fields, all nullable. That's the price of the pattern: a wide model with mostly-empty columns per row. The `entity_type` field is the discriminator your application code uses on read; DynamoDB itself ignores it. Don't try to query by `entity_type` alone — you'd need a GSI for that.

- **Name:** `11-single-table-many-to-many/` (three M:N approaches)
  - **What:** Three independent scripts demonstrating different tradeoffs for the same problem (Customer ↔ Merchant):
    - `s01_adjacency_list.py`: two rows per edge, `TransactWrite` for atomicity. 2× write cost, strong consistency both directions.
    - `s02_gsi_inversion.py`: one row per edge + an inverted GSI. 1× write cost, eventual consistency on the reverse direction.
    - `s03_composite_gsi.py`: dedicated `gsi_pk`/`gsi_sk` fields letting one GSI serve multiple relationship types.
  - **Why:** M:N has no single right answer in DynamoDB — every approach trades writes vs. consistency vs. flexibility. Folder 11 is the curriculum's payoff: the learner sees three working approaches side by side and gains the judgment to pick.
  - **Key files:** `examples/11-single-table-many-to-many/s01_adjacency_list.py:67-74` (TransactWrite for atomic edges), `s02_gsi_inversion.py:47-54` (InversionIndex).
  - **Gotchas:** Each script uses a **different table name** (`_st_mtm_adjacency`, `_st_mtm_gsi_inversion`, `_st_mtm_composite_gsi`) so all three demos can coexist. After running, `cleanup_all_tables.py` will find and clean all of them.

### examples/ — utilities

- **Name:** `examples/cleanup_all_tables.py`
  - **What:** Lists every table in the configured region whose name starts with `dynamodb_basic_opeartions`, prints them, asks for confirmation, then deletes them.
  - **Why:** Friction-killer. Without it, a learner who runs the full curriculum ends up with 15+ tables in their AWS account and has to delete each one by hand in the console. Re-runnable safely (it asks every time).
  - **Gotchas:** The match is **prefix only**. If a learner accidentally renamed their prefix in one script, that table won't be found and will linger.

## Conventions

- **Naming.** `s<NN>_<short_name>.py` — `s` for "step". `00–08` are independent; `09–11` are sequential within their folder.
- **Imports.** Top of every script: pynamodb classes, `from pynamodb_session_manager.api import use_boto_session`, `from dynamodb_basic_opeartions.one.api import one`.
- **Lifecycle.** `if not Model.exists(): create_table(wait=True)` → `for x in Model.scan(): x.delete()` → real work → optional commented `# Model.delete_table()`.
- **Session.** All DynamoDB calls inside `with use_boto_session(Model, bsm):` where `bsm = one.bsm`.
- **Models inline by default.** Most scripts define their `Model` class in the same file. The exceptions are `09-pipeline-metadata-demo/` and `10-single-table-one-to-many/`, which use a shared `models.py` because multiple scripts reuse the same model.
- **No `if __name__ == "__main__":` guards on examples.** Scripts are top-level procedural. Trade-off: simpler to read, but the scripts cannot be imported without running their side-effects. Folder utilities (`cleanup_all_tables.py`) are an exception.
- **Type checking via stubs.** `boto3-stubs[dynamodb]` is pinned alongside `boto3` for editor autocomplete; nothing at runtime depends on it.
