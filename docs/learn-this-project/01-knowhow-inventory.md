# 01 — Knowhow Inventory

## Project at a glance

**dynamodb_basic_opeartions** is a progressive, hands-on POC for **pynamodb** (Python ORM for DynamoDB) + **pynamodb-session-manager** (multi-account credential switching). It is organized as 12 independently runnable example folders (00–11), each teaching one DynamoDB concept — from a minimal model definition through CRUD, batching, query/scan, conditional writes, ACID transactions, secondary indexes, and single-table design. All examples use a coherent fin-tech domain (AxiomCard credit-card platform): cards, transactions, customers, merchants, and pipeline metadata. Every script runs against a real AWS account and is idempotent — tables are created once, rows are wiped on rerun.

## Architecture overview

```
dynamodb_basic_opeartions/          ← Python package (session/credential singleton)
 └── one/api.py → one              ← Central singleton: one.bsm, one.boto_ses, one.dynamodb_client

examples/                           ← 12 progressive tutorial folders + cleanup utility
 ├── 00-minimal-poc/               ← Golden reference skeleton
 ├── 01-attributes/ … 08-gsi-and-lsi/  ← Independent single-topic examples
 ├── 09-pipeline-metadata-demo/    ← Composite real-world demo (sequential)
 ├── 10-single-table-one-to-many/  ← Single-table 1:N (sequential)
 ├── 11-single-table-many-to-many/ ← Single-table M:N (independent patterns)
 └── cleanup_all_tables.py         ← Bulk table cleanup by prefix

pyproject.toml                      ← Dependencies: pynamodb, boto3, boto-session-manager, etc.
mise.toml                           ← Task runner: inst, test, cov, build-doc, etc.
```

Every example script follows the same skeleton: import `one.bsm` → define a Model → wrap DynamoDB calls in `with use_boto_session(Model, bsm):`. This pattern is the unifying thread.

## Component inventory

### 1. `dynamodb_basic_opeartions/one/` — AWS session singleton

- **What**: Provides a single `one` object with `bsm` (BotoSesManager), `boto_ses` (boto3.Session), and `dynamodb_client` (DynamoDB client) as cached properties.
- **Why**: Centralizes AWS credential configuration. Change the profile/region once in `one_03_boto_ses.py` and all examples follow. Avoids hardcoding credentials in every script.
- **Key files**:
  - `dynamodb_basic_opeartions/one/one_01_main.py` — Mixin composition: `class One(OneConfigMixin, OneBotoSesMixin)`
  - `dynamodb_basic_opeartions/one/one_03_boto_ses.py` — `OneBotoSesMixin`: `bsm` property reads `AWS_PROFILE` env var, region `us-east-1`
  - `dynamodb_basic_opeartions/one/api.py` — Exports the singleton: `one = One()`
- **Depends on**: `boto-session-manager`
- **Gotchas**: The `AWS_PROFILE` env var must be set (via `.env` file loaded by mise). If missing, boto3 falls back to default credentials, which may point at the wrong account.

### 2. `examples/00-minimal-poc/` — Golden reference

- **What**: One script (`s01_minimal_poc.py`) that demonstrates the complete skeleton: Model class, Attribute definitions, Meta inner class, `use_boto_session` context manager, and basic put/get.
- **Why**: This is the "copy this and modify" template. Every subsequent example folder builds on this pattern. It exists so learners have one clean reference to return to.
- **Key files**: `examples/00-minimal-poc/s01_minimal_poc.py`
- **Depends on**: `pynamodb`, `pynamodb-session-manager`, `one.api`
- **Gotchas**: None — deliberately minimal.

### 3. `examples/01-attributes/` — Attribute types

- **What**: Three scripts covering scalar types (`s01_basic_types.py`), collection types (`s02_collection_types.py`), and JSON attributes (`s03_json_attribute.py`).
- **Why**: DynamoDB attribute types are not 1:1 with Python types. pynamodb's attribute classes abstract this mapping; understanding them is foundational to writing correct models.
- **Key files**: `examples/01-attributes/s01_basic_types.py`, `s02_collection_types.py`, `s03_json_attribute.py`
- **Depends on**: `pynamodb` (UnicodeAttribute, NumberAttribute, BinaryAttribute, UTCDateTimeAttribute, BooleanAttribute, ListAttribute, MapAttribute, JSONAttribute)
- **Gotchas**: `JSONAttribute` stores arbitrary JSON but loses DynamoDB-native query/filter capabilities on the nested fields — use `MapAttribute` subclasses when you need to query inside the structure.

### 4. `examples/02-table-management/` — Table lifecycle

- **What**: Create/delete tables (`s01`), describe table metadata (`s02`), billing mode comparison (`s03`).
- **Why**: Understanding PAY_PER_REQUEST vs PROVISIONED billing and table creation latency is critical before running any example at scale.
- **Key files**: `examples/02-table-management/s01_create_and_delete.py`, `s02_describe_table.py`, `s03_billing_modes.py`
- **Depends on**: `pynamodb` Model.create_table / delete_table / describe_table
- **Gotchas**: `create_table` with `wait=True` blocks 5–30s. Examples keep tables alive to avoid this wait on reruns — only uncomment `delete_table()` when done.

### 5. `examples/03-crud-basic/` — Single-item operations

- **What**: Five scripts: save (`s01`), get (`s02`), update (`s03`), delete (`s04`), refresh (`s05`).
- **Why**: `save()` replaces the entire item (PutItem); `update()` patches specific attributes (UpdateItem). Confusing them is a common bug. `refresh()` re-reads from DynamoDB into a stale local object — useful after concurrent writes.
- **Key files**: `examples/03-crud-basic/s01_save.py` through `s05_refresh.py`
- **Depends on**: `pynamodb` Model CRUD methods
- **Gotchas**: `save()` without condition will silently overwrite existing items. Use conditional writes (folder 06) to prevent this.

### 6. `examples/04-batch-operations/` — Bulk read/write

- **What**: batch_write (`s01`), batch_get (`s02`), handling UnprocessedItems (`s03`).
- **Why**: DynamoDB limits batch operations to 25 items per request. pynamodb handles chunking, but UnprocessedItems can still occur under throttling — the `s03` script shows how to retry them.
- **Key files**: `examples/04-batch-operations/s01_batch_write.py`, `s02_batch_get.py`, `s03_batch_with_unprocessed.py`
- **Depends on**: `pynamodb` Model.batch_write / batch_get
- **Gotchas**: `batch_write` is not atomic — some items may succeed while others fail. Check `UnprocessedItems` in production.

### 7. `examples/05-query-and-scan/` — Reading data at scale

- **What**: Basic query (`s01`), sort + limit (`s02`), pagination (`s03`), scan + filter (`s04`).
- **Why**: `query` (O(result set)) vs `scan` (O(table size)) is the most important performance distinction in DynamoDB. This folder teaches when each is appropriate and how pagination works.
- **Key files**: `examples/05-query-and-scan/s01_query_basic.py` through `s04_scan_and_filter.py`
- **Depends on**: `pynamodb` Model.query / scan, range_key_condition, filter_condition
- **Gotchas**: `scan` reads every item in the table — never use it in production hot paths. Filters reduce returned data but not consumed capacity.

### 8. `examples/06-condition-expression/` — Conditional writes

- **What**: Save-if-not-exists (`s01`), update-with-condition (`s02`), optimistic locking (`s03`).
- **Why**: DynamoDB has no row-level locks. Conditional expressions are the only way to enforce invariants (e.g., "don't overwrite if already exists", "only update if version matches"). Optimistic locking is how you implement "edit without conflicts" in a lockless system.
- **Key files**: `examples/06-condition-expression/s01_save_if_not_exists.py`, `s02_update_with_condition.py`, `s03_optimistic_lock.py`
- **Depends on**: `pynamodb` condition expressions, `VersionAttribute`
- **Gotchas**: Condition failures raise `PutError` / `UpdateError` with a specific `ConditionalCheckFailedException` — catch it explicitly.

### 9. `examples/07-transactions/` — ACID across items

- **What**: TransactWrite (`s01`), transact with conditions (`s02`), TransactGet (`s03`).
- **Why**: DynamoDB transactions let you atomically write/read up to 100 items across multiple tables. The classic use case is a money transfer: debit account A and credit account B, or neither. Without transactions, a crash between the two writes leaves data inconsistent.
- **Key files**: `examples/07-transactions/s01_transact_write.py`, `s02_transact_with_condition.py`, `s03_transact_get.py`
- **Depends on**: `pynamodb` TransactWrite / TransactGet
- **Gotchas**: Transactions cost 2x the capacity of non-transactional writes. Use them only when atomicity is required.

### 10. `examples/08-gsi-and-lsi/` — Secondary indexes

- **What**: GSI basics (`s01`), GSI projections (`s02`), LSI basics (`s03`), GSI vs scan cost comparison (`s04`).
- **Why**: DynamoDB's base table only supports queries on the primary key. GSIs and LSIs create alternative access patterns without duplicating data manually. Understanding projection types (KeysOnly, Include, All) and the GSI eventual-consistency tradeoff is critical for cost-effective schema design.
- **Key files**: `examples/08-gsi-and-lsi/s01_gsi_basic.py` through `s04_gsi_vs_scan.py`
- **Depends on**: `pynamodb` GlobalSecondaryIndex, LocalSecondaryIndex, projection classes
- **Gotchas**: LSIs must be created at table creation time (cannot be added later). GSIs are eventually consistent — reads may lag 1-2 seconds behind writes.

### 11. `examples/09-pipeline-metadata-demo/` — Composite real-world demo

- **What**: Four sequential scripts + `models.py`. Sets up a Pipeline Metadata table, seeds 30 mock pipeline runs, demonstrates 3 query patterns, and compares scan vs GSI ConsumedCapacity.
- **Why**: This is where isolated concepts come together. It models a real AxiomCard use case (CI/CD pipeline tracking) with a composite key design (PK=pipeline_name, SK=run_id) and a GSI on status. The capacity comparison script (`s04`) makes the cost argument for GSIs concrete.
- **Key files**: `examples/09-pipeline-metadata-demo/models.py`, `s01_setup.py`, `s02_seed_data.py`, `s03_queries.py`, `s04_compare_capacity.py`
- **Depends on**: All prior concepts (model, CRUD, query, GSI)
- **Gotchas**: Must run scripts in order (`s01` → `s04`). The `models.py` is shared across all scripts in this folder.

### 12. `examples/10-single-table-one-to-many/` — Single-table 1:N

- **What**: Three sequential scripts + `models.py`. Single-table design with Customer → Card → Transaction all in one table, using composite sort keys (PK=`CUSTOMER#C001`, SK=`PROFILE` | `CARD#CD001` | `TX#CD001#2026-04-27T10:00:00`).
- **Why**: Single-table design is the canonical DynamoDB pattern for applications with known access patterns. It eliminates the need for JOINs (which DynamoDB doesn't support) by co-locating related entities. This is the mental model shift from SQL normalization.
- **Key files**: `examples/10-single-table-one-to-many/models.py`, `s01_setup_and_seed.py`, `s02_query_patterns.py`, `s03_query_card_transactions_by_date.py`
- **Depends on**: All prior concepts, especially composite keys and range queries
- **Gotchas**: Composite SK design requires careful prefix planning. If you change the SK format, existing data becomes unqueryable. Must run in order.

### 13. `examples/11-single-table-many-to-many/` — Single-table M:N

- **What**: Three independent scripts demonstrating M:N (Customer ↔ Merchant) relationships: adjacency list (`s01`), GSI inversion (`s02`), composite GSI (`s03`).
- **Why**: M:N relationships are the hardest DynamoDB modeling challenge. Each approach has distinct tradeoffs: adjacency lists require 2x writes but give strong consistency; GSI inversion is cheaper but eventually consistent; composite GSIs pack multiple relationship types into one index.
- **Key files**: `examples/11-single-table-many-to-many/s01_adjacency_list.py`, `s02_gsi_inversion.py`, `s03_composite_gsi.py`
- **Depends on**: GSI knowledge (folder 08), single-table design (folder 10)
- **Gotchas**: Each script is self-contained (unlike folders 09–10). Three different patterns — don't conflate them; each solves M:N differently.

### 14. `examples/cleanup_all_tables.py` — Bulk cleanup utility

- **What**: Lists all tables matching the `dynamodb_basic_opeartions_*` prefix and deletes them after user confirmation.
- **Why**: After working through the examples, the user's AWS account has many tables. This script cleans them all up safely using a prefix scan.
- **Key files**: `examples/cleanup_all_tables.py`
- **Depends on**: `boto3` DynamoDB client, `one.api`
- **Gotchas**: Asks for confirmation before deleting. Uses prefix matching to avoid deleting unrelated tables.

### 15. `dynamodb_basic_opeartions/paths.py` — Project path utilities

- **What**: Defines `dir_project_root`, `dir_home`, etc. as `pathlib.Path` objects for referencing project directories.
- **Why**: Enables consistent path resolution across scripts regardless of working directory.
- **Key files**: `dynamodb_basic_opeartions/paths.py`
- **Depends on**: `pathlib` (stdlib)
- **Gotchas**: None.

### 16. `dynamodb_basic_opeartions/tests/helper.py` — Test utilities

- **What**: Wrappers around vendored `pytest_cov_helper` for running unit tests with coverage.
- **Why**: Enables the `if __name__ == "__main__":` pattern in test files — each test file can be run standalone with coverage tracking.
- **Key files**: `dynamodb_basic_opeartions/tests/helper.py`, `dynamodb_basic_opeartions/vendor/pytest_cov_helper/`
- **Depends on**: `pytest`, `pytest-cov`
- **Gotchas**: None.

## Conventions

1. **Script naming**: `s01_`, `s02_`, etc. — numbering signals recommended reading order within a folder. Folders 00–08 are independent; 09–11 are sequential (run `s01` before `s02`).
2. **Model naming**: Table names use `dynamodb_basic_opeartions_` prefix. Model class names match the business entity (e.g., `Card`, `Transaction`, `PipelineRun`).
3. **Session wrapping**: Every DynamoDB operation is wrapped in `with use_boto_session(Model, bsm):`. This is not optional — without it, pynamodb uses its own connection pool, which may point at the wrong AWS account.
4. **Idempotent reruns**: Scripts scan and delete all existing rows at the start, then seed fresh data. Tables are kept alive (commented `delete_table()`).
5. **Imports**: Always `from dynamodb_basic_opeartions.one.api import one` then `bsm = one.bsm`.
