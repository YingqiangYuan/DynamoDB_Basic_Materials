# 03 — Elevation Roadmap

## Executive view

1. **Local DynamoDB testing** — Run examples against DynamoDB Local or LocalStack instead of a real AWS account, enabling offline development and CI integration.
2. **Observability and cost tracking** — Add ConsumedCapacity logging to every example and create a cost-awareness dashboard or summary.
3. **Error handling and resilience** — Demonstrate retry strategies, exponential backoff, and dead-letter patterns for failed writes.
4. **Advanced single-table design** — Extend the capstone with time-series patterns, hierarchical data, and write-sharding for hot partitions.
5. **CI/CD and automated validation** — Add GitHub Actions to run examples against DynamoDB Local, ensuring scripts stay runnable as dependencies evolve.

## Upgrade areas

### 1. Local DynamoDB testing

- **Current state**: All examples run against a real AWS account (`us-east-1`). The `one_03_boto_ses.py` singleton reads `AWS_PROFILE` from `.env`. There is no local alternative.
- **Senior-engineer target state**: Examples can run against [DynamoDB Local](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DynamoDBLocal.html) or [LocalStack](https://localstack.cloud/) by setting an environment variable (e.g., `DYNAMODB_ENDPOINT=http://localhost:8000`). CI runs all examples on every push without AWS credentials.
- **Alternatives**:
  - **DynamoDB Local (Docker)**: Official AWS tool. Free, accurate API parity. Tradeoff: no GSI/LSI eventual-consistency simulation, no throttling simulation.
  - **LocalStack**: Full AWS emulation. Tradeoff: heavier, community edition has limitations, may drift from real DynamoDB behavior on edge cases.
  - **Moto (mocking library)**: In-process mock. Tradeoff: fastest, but masks real latency/error behavior; not a true integration test.
- **Knowledge prerequisites**: Docker basics, endpoint override in boto3/pynamodb, fixture design in pytest.
- **Suggested learning path**:
  1. Docker fundamentals (run a container, expose ports)
  2. pynamodb's `host` attribute in `Meta` class
  3. pytest fixtures for setup/teardown of DynamoDB tables
  4. GitHub Actions with Docker services

### 2. Observability and cost tracking

- **Current state**: Only `examples/09-pipeline-metadata-demo/s04_compare_capacity.py` tracks ConsumedCapacity. Other examples don't report cost metrics.
- **Senior-engineer target state**: Every example prints `ConsumedReadCapacityUnits` / `ConsumedWriteCapacityUnits` after each operation. A summary script aggregates capacity usage across all examples for a "cost of learning" report.
- **Alternatives**:
  - **Per-operation logging**: Add `return_consumed_capacity='TOTAL'` to every query/scan/write call. Tradeoff: verbose but granular.
  - **CloudWatch metrics**: Use CloudWatch to monitor table-level metrics. Tradeoff: requires AWS Console access, not in-script.
  - **AWS Cost Explorer tags**: Tag tables and track costs at the billing level. Tradeoff: only useful for long-running tables, not POC scripts.
- **Knowledge prerequisites**: DynamoDB capacity units (RCU/WCU), pynamodb's `return_consumed_capacity` parameter, CloudWatch DynamoDB namespace.
- **Suggested learning path**:
  1. AWS DynamoDB pricing model (on-demand vs provisioned)
  2. pynamodb's Settings class and operation kwargs
  3. CloudWatch metrics for DynamoDB
  4. AWS Cost Explorer tagging

### 3. Error handling and resilience

- **Current state**: Examples use bare `try/except` for intentional failures (e.g., `ConditionalCheckFailedException` in folder 06) but don't demonstrate production-grade retry logic.
- **Senior-engineer target state**: A dedicated example folder demonstrating: exponential backoff with jitter, retry on `ProvisionedThroughputExceededException`, idempotent writes with client tokens, and a dead-letter pattern (write failures logged to a separate table or SQS queue).
- **Alternatives**:
  - **botocore retries**: boto3 has built-in retry configuration (`Config(retries={'max_attempts': 5, 'mode': 'adaptive'})`). Tradeoff: easy to enable, but limited control over retry logic.
  - **tenacity library**: General-purpose retry decorator for Python. Tradeoff: flexible, but adds a dependency.
  - **Custom retry with pynamodb**: Implement retry logic in a wrapper around pynamodb operations. Tradeoff: full control, but more code.
- **Knowledge prerequisites**: Exponential backoff with jitter, DynamoDB throttling behavior, idempotency tokens, SQS basics.
- **Suggested learning path**:
  1. AWS DynamoDB error handling best practices (AWS docs)
  2. botocore retry configuration
  3. Exponential backoff algorithm (the AWS blog post is canonical)
  4. SQS as dead-letter queue pattern

### 4. Advanced single-table design

- **Current state**: Folders 10–11 cover 1:N and M:N patterns with composite sort keys. These are solid but don't cover time-series, hierarchical data, or hot-partition mitigation.
- **Senior-engineer target state**: Additional examples for: (a) time-series data with TTL (e.g., transaction history auto-expiring after 90 days), (b) hierarchical data (org → team → member with begins_with queries), (c) write-sharding for hot partitions (appending a random suffix to the PK).
- **Alternatives**:
  - **Separate tables per entity type**: The SQL-normalized approach. Tradeoff: simpler mental model, but loses DynamoDB's single-request multi-entity access and requires "join" logic in the application.
  - **DynamoDB Streams + Lambda**: React to changes instead of pre-computing relationships. Tradeoff: async, eventually consistent, adds infrastructure complexity.
  - **ElastiCache as a read-aside cache**: Cache hot-path queries. Tradeoff: reduces DynamoDB read cost but adds operational overhead.
- **Knowledge prerequisites**: DynamoDB TTL, `begins_with` on sort keys, write sharding, DynamoDB Streams.
- **Suggested learning path**:
  1. Alex DeBrie's "The DynamoDB Book" (the canonical resource for advanced modeling)
  2. AWS re:Invent talks on DynamoDB design patterns (Rick Houlihan)
  3. DynamoDB TTL documentation
  4. Write sharding best practices (AWS docs)

### 5. CI/CD and automated validation

- **Current state**: No CI/CD pipeline exists. `mise.toml` has tasks for testing and building, but no GitHub Actions workflow.
- **Senior-engineer target state**: A GitHub Actions workflow that: (a) installs dependencies with `mise run inst`, (b) starts DynamoDB Local in Docker, (c) runs all example scripts against it, (d) runs `mise run cov` for unit tests, (e) reports coverage to Codecov.
- **Alternatives**:
  - **GitHub Actions + DynamoDB Local**: Free, fast, accurate. Tradeoff: requires Docker in CI.
  - **GitHub Actions + LocalStack**: Broader AWS emulation. Tradeoff: slower startup, potential for false positives.
  - **Manual testing only**: Keep the current approach. Tradeoff: scripts may rot as dependencies update.
- **Knowledge prerequisites**: GitHub Actions YAML, Docker services in CI, DynamoDB Local configuration, Codecov integration.
- **Suggested learning path**:
  1. GitHub Actions fundamentals (workflow YAML, runners, services)
  2. DynamoDB Local Docker image (`amazon/dynamodb-local`)
  3. Codecov GitHub Action
  4. mise in CI environments

### 6. Documentation and onboarding

- **Current state**: `README.rst` provides a high-level overview. `examples/README.md` has a good folder table and conventions. Individual scripts have inline comments but no per-folder README.
- **Senior-engineer target state**: Each example folder has a `README.md` explaining the concept, the progression, what to look for, and common misconceptions. A "cheat sheet" document maps DynamoDB concepts → example folder → key file.
- **Alternatives**:
  - **Sphinx docs with autodoc**: Auto-generate API docs from docstrings. Tradeoff: useful for the package, overkill for tutorial scripts.
  - **Jupyter notebooks**: Interactive versions of each example. Tradeoff: richer output (tables, charts), but harder to maintain and run headless.
- **Knowledge prerequisites**: Technical writing for tutorials, Sphinx basics, Markdown.
- **Suggested learning path**:
  1. Divio documentation system (tutorials vs how-to vs reference vs explanation)
  2. Sphinx tutorial
  3. Writing effective code comments

### 7. Security and credential management

- **Current state**: AWS credentials come from `AWS_PROFILE` in `.env`. The `.env` file is gitignored. No IAM policy scoping or credential rotation.
- **Senior-engineer target state**: A documented minimal IAM policy for running the examples (DynamoDB CRUD on `dynamodb_basic_opeartions_*` tables only). Optionally, AWS SSO integration instead of static credentials.
- **Alternatives**:
  - **AWS SSO (IAM Identity Center)**: Short-lived credentials, no long-lived keys. Tradeoff: requires org-level setup.
  - **IAM role assumption**: Use `sts:AssumeRole` with scoped permissions. Tradeoff: more config, but auditable.
  - **Current approach (named profile)**: Simple. Tradeoff: relies on user having a correctly scoped profile.
- **Knowledge prerequisites**: IAM policies, least-privilege principle, AWS SSO, STS AssumeRole.
- **Suggested learning path**:
  1. AWS IAM policy language
  2. DynamoDB resource-based ARN patterns
  3. AWS SSO / IAM Identity Center setup

## Projects-not-included

- **DynamoDB Streams + Lambda integration**: No example folder exists, but the AxiomCard domain (credit card transactions) naturally lends itself to event-driven processing. The omission is likely intentional — keeping the project focused on the data-modeling layer.
- **DynamoDB DAX (in-memory cache)**: No mention in the codebase. DAX is relevant for read-heavy workloads but adds infrastructure complexity beyond a POC scope.
- **Multi-region / global tables**: Not covered. Would be a natural extension for the AxiomCard domain (multi-region availability) but is beyond POC scope.
- **PartiQL queries**: pynamodb doesn't natively support PartiQL. A folder comparing pynamodb's query API to raw PartiQL via boto3 would be educational but departs from the pynamodb focus.
